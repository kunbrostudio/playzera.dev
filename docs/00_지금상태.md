**홈 레일 썸네일 반응형 버그 수정(STEP 25).** 썸네일 박스 높이가 뷰포트
높이(vh) 기준이라 화면 비율마다 모양이 뒤틀리던 걸 `aspect-ratio: 16/10`
고정으로 바꿨다(/me의 게임 카드와 통일). `perPage()` 문턱도 900 하나였던

3개로 늘렸다. 고치는 중에 "썸네일이 여전히 이상하다"는 재보고가 있었는데,
확인해 보니 원인은 다른 데 있었다 — 개발용 더미 카드(`placeholders.js`)가
정사각형 아이콘을 재활용해서, 새로 넓어진 16:10 박스에서 유독 작게 떠
보였다(실제 게임은 1.78:1 가로 이미지라 잘 맞는다). ken 요청으로
`registry.js`의 더미 주입을 꺼서(주석 처리, 파일은 보존) `npm run dev`에도
실제 게임만 보이게 했다.

**보류했다** — ken(180cm) 기준 2.6m였던 거리가 아이 키(4~8세, 102~128cm)로 계산하면

**손 스와이프로 레일 넘기기 완료(STEP 21).** `core/swipeGate.js` — 손을 빨리
옆으로 저으면(350ms 안에 화면 폭 14%) 페이지가 넘어간다. 화살표는 지우고
`.pz-peek`(옆 카드가 살짝 걸쳐 보이는 조각)로 대체했다. 확정 뒤 손이 원위치로
돌아오는 동작을 반대 스와이프로 오판하던 버그를 "정리 중(settling)" 상태로
고쳤다(손이 실제로 멈춰야 다음 판정을 연다). 손가락 모양(Fist/Palm) 기반 안은
MediaPipe Hands 모델이 있어야 해서 성능 실측 없이는 보류
(`play-zera-gesture-control-ux-spec.md` 참고, `docs/04` STEP 21).

`main`은 커밋까지 돼 있고 **푸시는 ken이 직접 한다**(맥 키체인에 인증이 있다).

**레일 스와이프 — 끝에 닿기만 해도 자동으로 넘어가던 버그 수정(STEP 23~24).**
1차: `core/edgeSwipe.js`가 무장 순간의 위치를 고정 anchor로 쓰던 걸 롤링 시간 창
(`windowMs` 기본 400ms)으로 바꿨다. 고정 anchor는 시간 제한이 없어서 손을
가만히 대고만 있어도 떨림이 수 초에 걸쳐 쌓여 문턱(3.5%)을 넘었다. ken이
"오른쪽은 이제 완벽한데 왼쪽에서는 여전히(스와이프 동작 없이) 넘어간다"고
재보고 — 몸을 가로질러 반대쪽 끝까지 손을 뻗을 때 도착 직후 관성으로
되튀는 동작이 롤링 윈도우만으로는 진짜 당기기와 구별이 안 됐다(위치만
보면 모양이 같다). 무장 직후 `armGraceMs`(정착 유예, 기본 200ms) 동안은
기준점을 계속 지금 자리로 옮겨 이 되튐을 흡수하도록 추가했다 — 예전
`swipeGate.js`의 "정리 중(settling)" 상태와 같은 발상. node 시뮬레이션으로
되튐을 흉내 내 150ms는 부족하고 200ms면 흡수되는 걸 확인했다(가정한
수치라 실기기 확인은 아직 안 됐다). `test/edgeSwipe.test.js` 17건.

연기(게임 화면)는 흰색에서 짙은 잿빛으로 바꿨다. `vite.config.js`에
`server: { host: true }`를 추가해서 `npm run dev`를 다시 켜면 같은
와이파이의 휴대폰에서도 열린다 — 단, 카메라는 HTTPS가 아니면 iOS
Safari가 안 열어 준다(`docs/STEP9`), 레이아웃·키보드 모드 확인용이다.

**스토리 화면 나가기 버튼 + 엔딩 두 장면화 + 여자 버전 이미지.** 스토리
화면(인트로·발견·엔딩)에 나가기(X) 버튼이 추가됐다 — 누르면 게임
자체의 처음(`location.reload()`)으로 돌아간다. 인트로 마지막 장면은
스킵 대신 "시작" 버튼이 뜬다(자동 넘김은 그대로). 엔딩이 장면 하나
(엄마의 감사 인사)에서 둘(+ 새 그림 · 소년의 작별 인사 + 폭죽·꽃가루)로
늘었고, 모든 미션을 다 깨면 결과 화면("한 번 더" 버튼) 대신 곧장
게임 처음으로 되돌아간다 — 목숨이 다해 끝난 판은 그대로 결과 화면을
본다. 소녀 버전 이미지 5장(인트로 평온·흔들림, 엔딩 둘)을 마저 채워
인트로 4장면·발견 2장면·엔딩 2장면 전부 소년/소녀 버전이 다 있다.

**포즈 사인판 좌우 양방향(STEP 27).** 런지·옆구리늘리기(상체숙이기) 사인판이
늘 한쪽 방향으로만 나왔다 — 채점(`poseMatch.js`)은 원래 아이가 어느 쪽으로
해도 통과시켰지만, 그림이 한쪽뿐이니 아이는 반대쪽을 할 생각을 못 했다.
이제 나올 때마다(레벨 번호로 시작값을 갈라 레벨끼리도 다르게) 번갈아
뒤집혀 나온다 — 장애물 개수·간격은 그대로다. 캐릭터도 사인판 방향에
맞춰 반전해서 보여주고, **카메라로 아이가 실제로 반대쪽을 하면 캐릭터가
그쪽을 따라간다**(포즈 채점이 이미 알고 있던 "어느 쪽으로 맞았나"를
그대로 넘긴다). 팔벌리기는 좌우 대칭이라 안 건드렸다.

**자동재생(auto-play) 모드(STEP 28).** 카메라도 키보드·터치도 안 쓰고
"영상처럼" 캐릭터가 알아서 다 피해서 무조건 클리어되는 모드. 카메라
준비 화면에 "자율주행 모드" 버튼을 새로 추가했다(`allowAuto` 옵션 —
기본 꺼짐, 쥬라기 대탐험 3D만 켬. 다른 게임은 자동조종을 아직 안
구현해서 버튼 자체가 안 보인다). 코스를 미리 아는 스크립트
(`runner/game/autopilot.js`, 2D·3D 공용)가 저수준 컨트롤만 직접 불러서
운동 기록(EXP·배지)은 하나도 안 쌓이고, 서버에는 재생했다는 기록만
남는다(`input_mode: 'auto'`). 다섯 레벨 전부 한 번도 안 맞고 끝까지
가는지 실제로 굴려서 확인했다(`test/autopilot.test.js`). 사인판 좌우
반전(STEP 27)도 자동재생에서 그대로 따라간다. 작업 중 템플릿 문자열
안 CSS 주석에 백틱을 또 썼다가(`readyScreen.js`) `test/sourceParses.test.js`가
잡아서 고쳤다 — CLAUDE.md에 이미 적힌 패턴을 일곱 번째로 겪었다.

**자동재생 다듬기 + 버튼 이름(STEP 29).** ken이 실기기로 자동재생을 직접
보고 넷을 짚었다. 큐브를 피한 뒤 일정 시간(0.5초)이 지나면 가운데
레인으로 돌아오게 했다(심리적 안정감) — 연달아 나오면 마지막 것만
기준으로 한 번만 돌아간다. 포즈 LEAD를 0.15초 → 1.5초로 늘려 벽에 닿기
직전이 아니라 한참 전부터 자세를 잡게 했다(실제 사용자도 미리 잡는
것과 맞춘다). 큐브 회피가 가끔 가운데를 건너뛰고 반대편까지 두 칸을
한 번에 움직이던 버그도 고쳤다(`assignCubeLane`이 인접한 한 칸만
고르도록 제한). 버튼 이름도 "자동으로 보기"→"자율주행 모드",
"키보드로 하기"→"키보드 모드"로 바꿔 둘 다 "무엇으로 조작하나"를
뜻하게 맞췄다.

**스토리 이전 버튼 컷 경계 버그(STEP 30-①).** 인트로·발견·엔딩은 여러
장면(컷)을 이어 보여주는데, 장면이 바뀔 때마다 "이전" 버튼이 꺼져
있었다(그 장면의 첫 줄이면 무조건 꺼지는 로직 — 전체 스토리의 첫 줄인지는
안 봤다). 앞에 다른 장면이 있으면(`canGoBack`) 첫 줄에서도 켜 두고,
누르면 이전 장면의 **마지막 줄**부터 이어받는다 — 줄이 하나로 이어지는
것처럼 보인다. 셋 다 같은 규칙이다.

**러너 속도 설정(STEP 30-②).** 기본 레벨 속도는 3~5세 기준이라, 7세
이상·초등학생도 할 수 있게 타이틀 화면(쥬라기 대탐험 3D)에 "속도 설정"
버튼을 추가했다 — 보통·빠르게·매우 빠르게 3단계 팝업. 레벨마다 새
숫자를 만들지 않고 기존 `speed`에 배율만 곱한다(반응 여유 시간
`approachSec`은 안 건드린다). localStorage에 남아 다음에도 유지된다.
작업 중 CSS 주석 백틱 버그를 두 번 더 냈다(이번 세션만 세 번째) —
`test/sourceParses.test.js`가 매번 잡았다.

**매우 빠르게 대폭 상향 + 배속 버그 두 개(STEP 31).** ken이 "매우
빠르게가 너무 느리다, 장애물이 다가오는 속도가 엄청 빨랐으면 좋겠다"고
재요청 — 파고들어 보니 숨은 버그 둘부터 고쳐야 했다. ① `play3d.js`가
화면 스크롤에 **배속 곱하기 전** 속도를 쓰고 있어서 배경은 그대로인데
장애물만 빨리 다가오는 어긋남이 있었다(`view.course.speed`로 수정).
② 판정 창(`atHit`)이 배속에 반비례해 좁아져서, 배율을 올릴수록 반응
속도 시험이 될 뻔했다 — `hitWindow`를 배속과 같은 비율로 넓혀 **실제
초 단위 여유는 배속과 무관하게 그대로**이도록 고쳤다(`buildCourse3d`).
이 보정 덕에 `veryFast` 배율을 1.6 → **2.5**로 크게 올렸다 — 화면이
훨씬 빨리 흐르면서도 판정 자체는 불가능해지지 않는다. 여전히
**실기기 검증 전**이다 — 어지러움·체감 난이도는 몸으로 해봐야 안다.

**속도 버튼 눈에 띄게 + 가로 폰 좌우 정렬(STEP 32).** ken이 모바일
스크린샷으로 확인하고 둘을 짚었다. 속도 버튼이 반투명이라 안 보여서
채운 민트색(시작 버튼의 금색과 안 부딪히는 색)으로 바꾸고 키웠다.
가로로 든 폰(iPhone SE 가로 등, 375px 높이)에서는 시작+속도가
위아래로 쌓이면 답답해 보인다고 해서, 다른 화면들과 같은 기준
(`max-height: 560px`)에서 이 둘만 좌우로 나란히 두게 했다 — 세로판은
안 건드렸다(이미 괜찮다고 확인됨). 마크업에 `.r3-title-actions`
컨테이너를 새로 감쌌다. 이 파일(`screens.js`)에서 CSS 주석 백틱 버그를
또 한 번 냈다가(이번 세션 세 번째) 커밋 전에 직접 잡았다.

**속도 버튼 그라데이션 + 스토리 화면 뒤로 버튼 제거(STEP 33).** 속도
버튼을 단색 파랑에서 `#0ECAFD → #0057EC` 그라데이션으로 바꿨다. 스토리
화면(인트로·발견·엔딩) 왼쪽 위 "뒤로"/"Home" 버튼은 없앴다 — 대사창 안
"이전"(컷 넘나드는 뒤로가기)과 나가기(X)→확인창의 "Home으로"(같은
`onHome` 핸들러)가 이미 같은 동작을 하고 있어서, 눈에 보이는 버튼만
정리했다. 기능은 그대로 확인창에 남아 있다.

쥬라기 대탐험(3D)은 그림·소리·코드가 다 갖춰져서 실기기(크롬) 검증만
남아 있다 — 속도 설정 3단계(매우 빠르게)가 어지럽지 않은지, 이번에
바뀐 속도 버튼·가로 폰 레이아웃·스토리 화면 버튼 정리가 눈으로 괜찮은지.

**새 게임 "오디세이 런" 기획 시작(STEP 34).** 쥬라기 런과 같은 엔진(3D
러너)을 오디세우스 귀환 여정 컨셉으로 재사용한다 — 6레벨(키클롭스 섬 →
세이렌·포세이돈 바다 → 스킬라·카리브디스 → 이타카 귀환+활쏘기). 기획
문서·콘셉트아트는 ken이 올렸고, `docs/04` STEP 34에 설계 확정 사항이
전부 있다. **핵심 전제: 사용자의 동작(달리기·로우)은 게임 진행에 전혀
영향을 안 준다** — 배는 항상 자동 전진하고 동작은 운동 지표로만
카운트된다(쥬라기 런과 똑같다). 그래서 물리·코스 로직을 새로 안 만들고
기존 `course.js`/`course3d.js`를 그대로 재사용했다.

바다+배는 아직 정식 게임이 아니다 — `runner3d` 엔진(scene·backdrop·
models·props)이 전부 쥬라기 전용으로 하드코딩돼 있어서, 정식 통합 전에
새 dev 화면 **`#/lab-sea`**에서 물·레인·성능만 먼저 본다(`#/lab3d`가
쥬라기 에셋 발주 전에 도형으로 먼저 쟀던 것과 같은 방식). 로우(노 젓기)
감지기(`core/pose/detectors/row.js`)도 새로 만들어 `#/lab`에 등록해 뒀다.

**쥬라기 대탐험(3D) STEP 26-33 배포 완료.** `main` 브랜치가 origin으로
푸시됐다(ken이 직접, 맥 키체인 인증) — Netlify가 `main`을 자동 배포한다.
오디세이 런 전용 파일 6개(`water.js`·`labsea.js`·`row.js`·
`test/row.test.js`, `router.js`·`lab.js`의 관련 diff)는 `git diff`로
100% 오디세이 전용임을 확인하고 이번 커밋에서 일부러 뺐다 — 어차피
DEV 전용 라우트라 프로덕션 빌드엔 안 들어가지만, 커밋 이력을 깔끔하게
나누려는 선택이었다.

**바다 셰이더 축 버그 발견 + 입체감 재설계(STEP 35).** ken이 `#/lab-sea`를
직접 보고 "물이 평평하다, 게임 스타일이지만 입체적으로" 피드백을 줬다.
원인은 축 버그였다 — `PlaneGeometry`는 `rotation.x=-π/2`로 눕히므로
로컬 **z**를 밀어야 화면에서 "위"로 움직이는데, 잔물결 코드가 실수로
로컬 **y**(회전 뒤엔 앞뒤 깊이 방향)를 밀고 있었다. 그래서 파도가
출렁이는 대신 미세하게 앞뒤로만 흔들려 "블라인드처럼 평평해" 보였다.
축을 고치고, 사인파를 셋(너울 둘 + 잔챙이 하나)으로 늘리고, 물결 기울기의
미분으로 가짜 노멀을 만들어 마루/골에 밝기 차를 주는 라이팅을
추가했다(`ground.js`의 `bakeShade()` 철학을 매 프레임 계산으로 옮긴
버전 — 실시간 조명 0개 규율은 그대로 지킨다). 텍스처도 가로 줄무늬(타일링
시 블라인드로 보이던 원인 중 하나)에서 방향 없는 얼룩 무늬로 바꿨다.
ken이 직접 보고 "대박이야! 멋져!"로 확인 완료 — 축 버그 진단이 맞았다.

**부표 경계물 추가(STEP 36).** ken이 물 확인 직후 이어서 요청 — 육지
러너는 연석(턱 있는 상자)으로 트랙과 잔디를 가르는데, 바다에도 "레인
바깥은 열린 바다"를 표시할 것이 있어야 한다고. ken 제안대로 부표로
풀었다. `props.js`의 `PropRow`(트리·바위가 이미 쓰는 인스턴싱+되돌리기
공용 모듈)를 그대로 재사용해서 로프 바로 바깥에 흩어 세웠다 — 새 배치
로직을 짜지 않았다. `PropRow`에 `bob`(까딱임) 옵션을 새로 추가했다
(기본값 없음 = 육지 프롭은 그대로, 물에 뜬 것만 켠다) — 물건마다 x·z에서
위상을 뽑아 흔들어서 부표 전부가 같은 박자로 까딱이지 않는다(`DinoRow`가
공룡 위상을 흩뜨리는 것과 같은 이유). 부표 자체는 원기둥 셋+구 하나를
`BufferGeometryUtils.mergeGeometries`로 한 지오메트리에 합치고 정점
색을 구워(빨강/흰색 몸통 + 회색 기둥 + 주황 꼭대기 표식) draw call
하나로 그린다. 테스트 793건(+3, `PropRow.bob` 신규)·빌드 통과.

**부표 확대 + 돌고래·섬·하늘 배경 + 배 GLB(STEP 37).** ken이 물·부표를
직접 보고 "대박이야! 멋져!"로 확인한 뒤 바로 이어서 요청 4개.

1. **부표 간격 확대** — 로프(±2.5, 가운데 레인 하나의 경계) 바로 바깥이
   아니라 트랙 전체 폭(`TRACK_W/2`≈7.5) 바깥으로 옮겼다. "부표를 더
   넓혀야 할 거 같아, 트랙을 3분할로 나눠야 하니까"라는 지적대로 —
   전에는 부표가 가운데 레인 하나만 감싸는 것처럼 보였다.
2. **돌고래** — `props.js`의 `bob`(사인파 하나)로는 "대부분 물 아래
   숨어 있다가 이따금 포물선으로 튀어오르는" 동작을 못 내서, `labsea.js`
   안에만 있는 `LeapingRow`를 새로 짰다(아직 여기 하나뿐이라 공용
   모듈로 안 올렸다). 정점색으로 구운 몸통(등 회청·배 흰색 그러데이션)
   +코+등지느러미+수평 꼬리지느러미(물고기와 구분되는 부분) 하나를
   합쳐 draw call 하나로 좌우 각 3마리씩 띄운다. 대부분 시간은 물 아래

어린 아이는 이걸 오류로 느끼거나 포기할 수 있다고. **코드부터 쓰지
말고 원인·대안을 먼저 정리해 달라**는 요청대로 조사부터 했다 —
`zoneDetector.js`(똥 피하기 전용)는 칸 폭을 카메라 프레임 전체
너비의 몫으로 계산해서 생긴 문제였고, 러너 엔진(쥬라기 대탐험 3D·
웜업)은 애초에 다른 코드(`moves.js`, `bodyHeight` 비율로 이미
정규화됨)를 써서 같은 문제가 없다는 걸 먼저 알렸다. 대안 두 개(A:
칸 폭 계산만 몸 기준으로 바꾸고 미러링 느낌 유지 / B: 러너처럼
상대적 스텝 방식으로 전면 교체)를 제시했고 ken이 **A**를 골랐다 —
단, "최소한의 이동으로도 반응해야 하지만 너무 예민해서 살짝만
움직여도 반응하는 건 비추"라는 조건을 붙였다. `zoneDetector.js`가
이제 골반뿐 아니라 코·발목도 읽어 `bodyHeight`를 계산하고, 칸 폭을
`LANE_STEP(=laneThreshold×2=0.24) × bodyHeight`로 재되 바닥값(0.10,
너무 예민해지지 않게)과 천장값(`1/n`, 원래보다 어려워지지 않게)으로
감싼다 — 카메라 거리·칸 수와 무관하게 칸 하나 넘기는 실제 이동량이
일정해진다. PIP 오버레이(`pipOverlay.js`)의 등분선은 이번엔 그대로
뒀다(ken이 "크게 고치지 말고 이것만"이라고 범위를 좁혔다) — 화면
선이 실제 경계보다 살짝 바깥에 그려지지만 기능은 안 깨진다.

테스트를 새 동작에 맞게 다시 썼다(`zoneDetector.test.js` 12건,
`poseEngine.test.js`의 관련 테스트도 전신 랜드마크로 수정) — 804건
전부 통과·빌드 통과.

**풍선 팡팡 — 좌표 보정 이후 두 번째 실기기 피드백 5건(STEP 76 후속
라운드 2).** ken이 좌표 보정판을 실기기로 다시 해보고 "잡는 것 자체는

느려서, 새 랜드마크가 도착할 때까지 화면이 이전 값을 들고 있다가 한
번에 점프하는 것으로 보인다 — 감지 자체를 빠르게 할 방법은 없어서

같은 보간된 좌표를 먹였다 — 약 80ms의 지연이 생기지만 "뚝뚝 끊김"보다
"부드럽게 따라옴"이 이 게임엔 맞는 트레이드오프라고 판단했다. 나머지
넷: ① 바구니를 ken이 지정한 두 번째(넓적한) 그림으로 교체
(`assets.js`의 `BASKET_IMAGE`) — 원래 그림은 세로 비율이 커서 화면
아래 자리에서 두꺼워 보였다. ② 잡은 풍선이 사라지지 않고 바구니
안에 쌓이는 그림(`#bf-basket-pile`)을 추가해 "성공했다"를 눈으로
확인할 수 있게 했다 — 스테이지가 바뀌면 비운다. ③ 풍선 개수를
스테이지마다 4~12개로 크게 올렸다(원래 1~5개, 어림값·주석으로
남김) — "처음부터 많이 보여줘도 될 거 같다"는 요청, 최종 밸런스는

줄었는지는 ken이 직접 봐야 안다.

**풍선 팡팡 — 세 번째 실기기 피드백: 트래킹 지속·바구니 재설계·잡기 1개
제한·판정 글자·타이머 진행(STEP 76 후속 라운드 3).** ken이 두 번째
스크린샷 2장(양손으로 여러 풍선을 동시에 잡은 모습, 작은 바구니 위에
아이콘이 어색하게 얹힌 모습)과 함께 다섯 가지를 짚었다.

가장 중요하다고 짚은 건 **여전한 손 트래킹 어색함**이다 — 원인을 다시
보니, 라운드 2의 스무딩(`smoothHands`)이 "이번 프레임에 좌표가 없으면
`smooth[side]`를 곧장 `null`로 지우는" 코드를 그대로 갖고 있었다.
`handTracker.js`의 신뢰도 문턱(0.65) 근처에서 값이 자주 잠깐씩
흔들리는데, 그때마다 커서가 사라졌다가 **보간 없이** 새 좌표로
순간이동했다 — "부드러워지긴 했는데 여전히 뚝뚝 끊긴다"는 재확인의
실제 원인일 가능성이 크다. 좌표가 없는 프레임엔 마지막 값을 그대로
유지하도록 고쳤다(`ui/playScreen.js`) — 커서가 화면 밖으로 사라지지
않고 그 자리에 멈춰 있다가, 손이 돌아오면 그 순간부터 다시 지수
보간으로 부드럽게 따라붙는다. ken이 요청한 "손이 사라져도 커서 유지 →
돌아오면 다시 따라가기"와 "여전한 끊김" 둘 다 같은 코드 한 군데의
문제였다. 대가로 손이 실제로 오래 사라지면 커서가 그 자리에 얼어붙어
드물게 우연한 판정에 걸릴 수 있다 — 혼자 하는 캐주얼 게임이라 감수했다.

`clamp(220px,34vw,440px)`로 키웠다. ③ **한 번에 하나만 잡힌다** —
`game.js`의 CATCH 로직에 "이미 붙잡힌 풍선이 있으면 다른 손은 이번
틱에 새로 못 잡는다" 제약을 추가했다(같은 프레임에 양손이 동시에
서로 다른 풍선을 잡는 경우까지 막았다). ④ **판정 글자** — 손이 닿아
붙잡는 순간 "Catch!", 바구니에 넣거나(1부) 터뜨리면(2부) "Great!"가
뜬다. 새로 만들지 않고 쥬라기 런의 장애물 판정 모듈(`runner/ui/cues.js`)을

명시적으로 요청했고, 이 모듈은 애초에 DOM 컨테이너 하나(`#pz-judge`)만
있으면 어느 게임에서도 동작하도록 만들어져 있었다(러너 3종이 이미
공유 중). `catch` 판정을 새로 추가하고 청록색(`--pz-blue-start`, 속도
설정 버튼과 같은 계열)을 입혔다 — 초록(Great)·분홍(Miss)과 안 겹치는
세 번째 색이다. `grab` 이벤트는 EXP 지표(`handHits`)에는 안 센다 —
collect까지 세면 풍선 하나당 손 움직임이 두 번(잡을 때+넣을 때)
카운트돼 운동량이 부풀려진다. ⑤ **타이머로만 진행** — "이 게임은
목숨값 그런 것은 없고 타이머로 설정해서 진행하자"는 요청대로, 원래

잡기 파트는 이제 "한 번에 하나만" 제약까지 겹쳐 시간이 더 걸리므로
15~30초, 터뜨리기 파트는 12~30초로 어림잡았다 — 전부 실기기 조정
대상이다.

`npm run check` — 테스트 926건 통과(신규 4건: grab 이벤트·한 번에 하나만·

**★ 리모컨이 화면 안을 짚는다 — 포커스 + 방향 이동(STEP 75).** 컨트롤러
작업의 핵심 덩어리. 명령이 `navigate` 하나뿐이라 게임 안에 들어가면 보낼
게 없었는데(내부 화면은 라우트가 아니다), 이제 `dir`·`ok`로 화면 안의

**화면마다 할 일이 없다 —** 이 저장소가 이미 모든 아이용 버튼에
`data-pz-hit`을 달아 두고 있어서(68곳, CLAUDE.md 규칙), "부모가 폰으로
누를 것 = 아이가 손으로 누를 것"이 그대로 성립한다. 스토리 스킵·준비
화면·결과 화면이 공짜로 따라오고 앞으로 만들 게임도 자동이다.

방향 계산은 `core/spatialNav.js`에 **순수 함수로** 뗐다 — 잘못 고르면
화면을 봐야만 아는 버그라 실기기에서 못 잡는다. 부축 어긋남에 벌점을 주고
같은 줄이면 깎는다(카드 레일에서 옆 카드가 아래 큰 버튼에 지지 않게 하는
항). 줄 끝에서는 **안 감긴다** — 3m 떨어져 보면 왜 반대쪽으로 갔는지
모른다. `core/focusNav.js`는 그걸 DOM에 붙이는데, 화면이 `innerHTML`로
갈리는 걸 견디려고 표시를 **따로 떠 있는 링**으로 만들었다. **리모컨이
붙어 있을 때만 켠다** — 안 그러면 관찰자·rAF가 늘 돌고, 아무도 조종
안 하는데 노란 링이 뜨면 아이에게 설명할 수 없는 표시가 된다.
테스트 1033건 통과(신규 48건).

**리모컨 재연결·세션 유지(STEP 74).** ken 질문: "폰 화면이 꺼졌거나 다른
앱을 열어도 연동이 계속 이어져 있나?" 답은 **아니오**였고, 파 보니 함정이
셋이었다.

**제일 아팠던 건 주 디바이스가 같은 폰의 재입장을 막고 있던 것이다.**
`_onJoin`이 "이미 붙어 있으면 무시"였는데, 두 번째 리모컨을 막으려던 게
**끊겼다 돌아온 같은 폰까지** 막았다. 주 디바이스는 리모컨이 사라진 걸
모르니 계속 붙어 있다고 믿고 문을 안 열어 준다 — 결국 QR을 다시 찍어야
했다. 이제 `remoteId`가 같으면 재입장으로 보고 승인창 없이 받아 준다(그
값은 승인받은 폰만 아는 토큰이라 아는 것 자체가 승인의 증거다).

나머지 둘: 페어링을 아무도 기억하지 않아 탭이 버려지면 통째로 잊었고
(`remoteStore.js` 신규 — **코드만이 아니라 `remoteId`까지** 저장해야
승인창이 다시 안 뜬다), 채널이 죽었는지 판단하려 들지 않고
`visibilitychange`·`online`에서 그냥 버리고 새로 만든다. 곁들여 재우는
동안 눌린 명령 하나를 들고 있다가 붙은 뒤 보낸다 — 없으면 "리모컨이 가끔
안 먹는다"가 된다. 심장박동은 일부러 안 넣었다(리모컨을 탁자에 뒀다고
TV가 연결을 끊지 않는 것과 같다). 테스트 983건 통과.

**★ 리모컨을 컨트롤러로 다시 정의 — 미러링 걷어냄(STEP 73).** ken이
실기기로 QR 페어링을 확인했다(폰으로 QR 찍기 → 연결 → 폰에서 게임 골라
시작하니 PC가 그 게임을 시작). 다만 **거기까지만** 됐다 — 명령이
`{type:'navigate', path}` 하나뿐이라 게임 안에는 보낼 게 없었다. 게임의
내부 화면(타이틀·준비·스토리·결과)은 라우트가 아니라서다.

방향을 정했다: **태블릿이 화면이고 폰은 입력이다.** 감시가 아니라 조작
편의가 목적이고(ken: "쉽게 다른 모바일로 컨트롤할 수 있게 하는 편의"),
아이가 큰 화면을 보는 한 폰에 같은 화면을 다시 그릴 이유가 없다. 그래서
미러링을 통째로 지웠다 — 게다가 `captureStream()`이 캔버스만 잡아
HUD·버튼이 안 찍히고 DOM 게임(풍선 팡팡)은 비출 것도 없는, 고칠 수 없는
구멍이 있었다.

앞으로 만들 것: 폰이 **D패드(좌·우·선택·상·하) + 상단 탭바 + 가로
썸네일 그리드**를 갖는 전용 컨트롤러 화면. 화살표는 태블릿 화면 안의
포커스를 옮기고, 폰 그리드는 태블릿 상태를 비추는 거울이라 둘이 어긋날
일이 없다. 남은 순서는 재연결·세션 유지 → 태블릿 포커스/방향 이동 →
컨트롤러 화면 → 명령 배선 → 준비 화면 O자세 건너뛰기. 테스트 952건 통과.

**풍선 팡팡 — 단계를 개수 목표로, 공통 UI 배선, 나가는 길 정리(STEP 76
후속 라운드 6).** 트래킹은 ken이 실기기에서 확인해 줬다("트래커 너무 잘
돼! 끊김없이 부드럽게") — 라운드 5의 두 원인이 맞았다.

이번 라운드의 핵심은 **단계 구조를 세 라운드 만에 제대로 읽은 것**이다.
`quota`(넘어가는 조건: 5·10·15개) · `timeLimitSec`(제한 시간: 1분) ·
`count`(화면에 뜨는 수: 5·7·10)가 각자 다른 축인데, 3차에서 "타이머로
진행"을 클리어 조건으로 읽어 quota를 걷어냈고 5차에서 개수를 화면에
뜨는 수로 읽었다. 이제 셋이 각자 이름을 갖고 테스트로 고정돼 있다.
시간 안에 목표를 못 채우면 실패이고(하트는 안 깎는다) 짧은 안내 뒤
타이틀로 돌아간다 — 4차에 ken이 요청했던 흐름이 이제야 의미가 생겼다.

**"다시 하기"가 허브로 가던 버그**도 잡았다. 원인이 둘 — `getBackTo()`가
registry에 `intro` 라우트가 없는 게임에 대해 `'/'`(허브)를 내는데 이
게임은 타이틀·인트로가 `play.js` 안에 있어서 항상 허브였고, "다시
하기"는 플레이 함수를 자기 안에서 재진입해 타이틀을 건너뛰었다.
`runBalloonPlay`가 이제 `'again' | 'home'`만 돌려주고 `play.js`가
타이틀부터 한 바퀴를 돈다. 곁들여 그동안 이 게임만 따로 그리고 있던
나가기 버튼을 걷고 **공통 시스템바**(햄버거·나가기·종료 확인)를 받아
썼다 — CLAUDE.md가 못박아 둔 바로 그 규칙을 어기고 있었다. 스토리
스킵도 셋 다 켰고(모듈은 원래 지원하고 있었다), 타이틀 시작 버튼을
화면 한가운데로 옮겼다. 테스트 969건 통과.

**★ 포즈 엔진이 골반 하나 때문에 통째로 침묵하고 있었다(STEP 76 후속
라운드 5) — 앱 전체에 영향.** ken이 다섯 번째로 "트래킹 여전히 안
된다"를 보내면서 스크린샷을 같이 줬는데, 라운드 4에서 붙여 둔 감지율
표시가 **`0회/초`**를 찍고 있었다(정상이면 15~30). 이 숫자가 없었으면
이번에도 스무딩 상수를 또 만졌을 것이다.

원인은 `personLock.js`였다. 사람의 "자리"를 **골반 중심으로만** 쟀는데,
골반이 안 보이면 점수가 `-Infinity`가 되고 → `select()`가 null →
`poseEngine._loop`이 **구독자를 아예 안 부른다**. 추론은 멀쩡히 도는데
랜드마크가 한 개도 안 나간다. ken은 책상 앞에 앉아 카메라 가까이서
테스트했고, 그러면 골반이 프레임 밖이거나 책상에 가린다 — 손·얼굴·
어깨는 다 잡히는데 골반 하나 때문에 전부 버려지고 있었다. 자리를
골반 → **없으면 어깨**로 떨어뜨려 고쳤다(`anchorOf`). **모든 게임이
같은 엔진을 쓴다** — 앉아서 하거나 카메라에 가까이 선 아이는 어느
게임에서도 인식이 끊겼을 것이고, 지금까지 안 드러난 건 서서 하는
게임을 서서 테스트했기 때문이다.

곁들여 트래커(손을 따라다니는 동그란 포인터 — ken의 용어로 통일했다)
두 개 문제도 잡았는데, 원인이 **둘**이었다: 지어낸 손목(Pose는 안 보이는
관절도 좌표를 채운다)과, 라운드 4에서 내가 만든 "얼어붙은 트래커"
(`handSmoother`가 한 번 생긴 손을 절대 null로 안 돌려줬다). 앞은 트래커를
**하나로 줄여서**, 뒤는 0.5초 실측이 끊기면 버리게 해서 막았다. 트래커
자리도 손목에서 **손바닥 한가운데**로 옮겼다. 바구니는 ken이 보낸 참고
그림대로 풍선을 키우고(24% → 62%) 겹침을 개수에 맞춰 계산하게 했다
(`pile.js`). 스테이지는 풍선 5 → 7 → 10개 3단계(각 20초, 합쳐 1분).
테스트 965건 통과. `#bf-diag`도 `추론 N/s · 사람 N/s · 손 N/s`로 나눠
찍는다 — 합쳐 보여줬으면 이번에도 어디가 막힌 건지 몰랐을 것이다.

**풍선 팡팡 — 손 트래킹을 지수평활에서 예측 필터로 다시 짬 + 바구니
겹침 재배치(STEP 76 후속 라운드 4).** 라운드 3을 올렸는데도 ken이
"트래킹 여전히 잘 안돼! 제발 트래킹 잘 되게 좀 해줘"로 재확인 —
숫자만 또 조정하는 대신 구조를 다시 봤다. 두 가지 원인을 찾았다.
① 문턱(라운드 2에서 0.65로 올린 값)이 너무 엄격해서, 팔을 뻗는(이
게임의 기본 동작) 정상적인 손목도 자주 걸러져 감지 자체가 뜸해졌다 —
"두 커서" 버그는 문턱이 아니라 "두 손목이 서로 너무 가까이 찍히면
신뢰도 낮은 쪽을 버린다"는 더 원인에 가까운 검사(`resolveWrists()`,
`handTracker.js`)로 따로 잡고, 문턱은 앱 표준(0.5)으로 되돌렸다.
② 지수평활 자체가 구조적으로 "뒤에서만 쫓아가는" 방식이라 느려
보였다 — `arcade2d/handSmoother.js`(신규)로 위치+속도를 함께 추정하는
예측 필터(alpha-beta 필터)를 새로 만들어, 진짜 새 감지가 있을 때만
보정하고 그 사이엔 마지막 속도로 미리 나가게 했다("진짜 새 감지"는
`handTracker.js`가 실제 갱신 때만 올리는 `hands.seq`로 구별한다 —
화면 좌표 계산 자체는 매 프레임 다시 하므로 값만 보고는 구별이 안
된다). 손이 사라지면 속도가 서서히 줄어 미끄러지다 멈춘다(끝없이
안 나간다). 두 모듈 다 순수 함수라 카메라 없이 테스트했다(`test/
handTracker.test.js`·`test/handSmoother.test.js`, 14건 신규) — 특히
"fresh가 5프레임에 한 번만 와도 그 사이에 위치가 계속 움직이는지"를
직접 검증했다. 화면 구석에 실제 감지 주기를 작게 표시하는 진단
문구도 추가했다(`#bf-diag`, `status:'wip'`에서만 신경 쓰면 되는 개발용
표시) — 다음에 재확인받을 때 "느낌"이 아니라 숫자(초당 몇 회
감지되는지)로 원인을 좁히기 위해서다.

곁들여 바구니 쌓임 방식도 다시 바꿨다 — ken이 "위로 쌓이지 말고
그냥 한 줄로 겹치게, 바구니 뒤로"라고 정정해서, 라운드 3의 "경계선에서

**로딩 화면 깜빡임 수정 + 디자인 토큰 시스템(STEP 74).** ken이 로컬(캐시 있는

싱글톤 `core/remote/controller.js`(리모컨 쪽, `session.js`의 반대편) +
`remote.js`는 승인만 받는 부팅 화면으로 축소(승인되면 `location.hash

닫히고 역할(주 디바이스/조종 중)에 따라 다른 패널을 연다 +

프로토콜도 `start`/`stop` 둘에서 `{type:'navigate', path}` 하나로
단순해졌다. **화면 미러링("화면 보기")은 이번엔 뺐다** — 리모컨이
허브에 머무르므로 비출 게임 화면 자리가 없어졌다, ken 확인 "일단
빼기"(코드는 안 지움). 새 테스트 14건(controller.js 10건 + session.js
연결끊기 알림 4건) — 861건 전부 통과·빌드 통과. **navigate() 가로채기가
실제 브라우저에서 도는지 전부 실기기 미검증.**

**부모 리모컨 2단계 — 화면 미러링(STEP 65).** "다음 단계까지 진행하자"는
ken 지시로 바로 구현하기 전에 가정부터 검산했다 — `canvas.captureStream()`은
게임 캔버스(세계·캐릭터)만 잡고 그 위 HUD(DOM)는 안 잡힌다는 것, 캔버스가
아예 없는 순수 DOM 게임(불 끄기·돌다리·팝팝 클리커, 전부 `status:hidden`)은
이 방식으론 못 비춘다는 것, `getDisplayMedia`(화면 공유)는 대안이
아니라는 것(2026년 현재도 아이폰·안드로이드 모바일 브라우저 전부
미지원, 데스크톱 전용 API)을 확인했다. 지금 노출된 세 게임은 전부
캔버스 기반이라 실사용엔 지장 없어 — 범위를 "게임 세계만"(HUD 숫자는
다음)으로 좁혀 진행했다. `session.js`에 `mirror-request`/`mirror-stop`/
`webrtc-answer`/`webrtc-ice` 신호(같은 Realtime 채널 재사용, TURN 없이
STUN만) + 화면 전환마다 캔버스를 다시 찾아 연결을 갈아 끼우는
`_reconcileMirror()` 추가. 리모컨(`remote.js`)엔 "화면 보기" 토글 +
video 엘리먼트. 자동으로 안 켜진다 — 리모컨이 눌러야 인코딩이
시작된다(성능 예민, `#/lab3d`와 같은 이유). 가짜 `RTCPeerConnection`으로
신호 흐름 10건 신규 테스트 — 846건 전부 통과·빌드 통과. **영상이
실제로 뜨는지·지연·FPS 영향은 전부 실기기 미검증.**

**부모 리모컨 1단계 — QR 페어링 + 켜고끄기/게임고르기(STEP 64).** 다인

미룸). 페어링은 QR — 열 때마다 새 코드로 새 채널을 만들고(고정 QR
아님) 주 디바이스가 매번 승인해야 붙는다("화면을 봐야 스캔할 수
있다"는 물리적 제약이 보안 경계다, Realtime 자체는 "같은 와이파이"를
강제 못 함). 새 싱글톤 `core/remote/session.js`(주 디바이스, 페이지를
넘나들어도 산다) + `pairingModal.js`(홈의 QR 아이콘, `qrcode` 패키지

15건 신규(가짜 채널로 승인 흐름·명령 처리 확인, 실제 네트워크는
실기기 필요) — 836건 전부 통과·빌드 통과. `npm run check`의 에셋
예산 실패는 이번 작업과 무관(이전부터 있던 것, `git stash`로 확인).
**QR 스캔→페어링 전체 흐름·아이패드 사파리 렌더링 전부 실기기 미검증.**
2단계(WebRTC 영상 미러링, `canvas.captureStream()` 방향으로 설계만
됨, TURN 서버 없이 시작하기로 함)는 다음 세션.

**다인 카메라 인식 — 두 단계 잠금 방식으로 구현(STEP 63).** 여러 턴에
걸친 설계 대화 끝에(① 미래 회원 얼굴 인식 기능과 자리를 맞출 것,

시작 동작이라 아이에게 새로 시키는 게 없다), **잠긴 뒤**는 위치

구독자에게 넘긴다. `readyScreen.js`의 `finish('motion')` 한 곳에
