## 어디까지 왔나

코드는 게임 8개, **서버(허브)에 보이는 건 셋뿐**(똥 피하기·쥬라기 대탐험(3D)·
인터랙션 웜업) — 나머지 다섯은 `status: hidden`으로 보관, 코드는 안 지웠다.
자세한 이유는 `CLAUDE.md`의 "지금 위치" 표. 테스트 790건 · **크롬에서만 확인됨.**

**홈 레일 썸네일 반응형 버그 수정(STEP 25).** 썸네일 박스 높이가 뷰포트
높이(vh) 기준이라 화면 비율마다 모양이 뒤틀리던 걸 `aspect-ratio: 16/10`
고정으로 바꿨다(/me의 게임 카드와 통일). `perPage()` 문턱도 900 하나였던
걸 480/900 둘로 나눠, 가로로 누운 폰이 세로 폰과 똑같이 2개만 보이던 걸
3개로 늘렸다. 고치는 중에 "썸네일이 여전히 이상하다"는 재보고가 있었는데,
확인해 보니 원인은 다른 데 있었다 — 개발용 더미 카드(`placeholders.js`)가
정사각형 아이콘을 재활용해서, 새로 넓어진 16:10 박스에서 유독 작게 떠
보였다(실제 게임은 1.78:1 가로 이미지라 잘 맞는다). ken 요청으로
`registry.js`의 더미 주입을 꺼서(주석 처리, 파일은 보존) `npm run dev`에도
실제 게임만 보이게 했다.

쥬라기 대탐험(3D, 옛 이름 "쥬라기 런 3D")은 타이틀 → 카메라 준비 → 튜토리얼 →
판 → 결승 포털 → 엔딩 → 결과까지 한 바퀴가 다 돈다.

`#/labcam` 실측 완료(STEP 20) — 세로가 화각을 넓혀줄 거라는 예상은 **틀렸다**
(맥북캠은 오히려 좁아짐). 관절 요구를 줄이는 쪽(6/8 게임 통과로 바뀜)은 확인됐지만
**보류했다** — ken(180cm) 기준 2.6m였던 거리가 아이 키(4~8세, 102~128cm)로 계산하면
1.47~1.85m다. 실제 이용자 기준으로는 처음 생각만큼 급한 문제가 아니고, 고치려면
`moves.js`의 현장 튜닝값을 다시 잡아야 해서 위험 대비 이득이 낮다. `pose/requirements.js`·
`#/labcam`은 코드로 남아 있으니 실기기 검증에서 실제로 불편하면 그때 꺼내 쓴다.

**손 스와이프로 레일 넘기기 완료(STEP 21).** `core/swipeGate.js` — 손을 빨리
옆으로 저으면(350ms 안에 화면 폭 14%) 페이지가 넘어간다. 화살표는 지우고
`.pz-peek`(옆 카드가 살짝 걸쳐 보이는 조각)로 대체했다. 확정 뒤 손이 원위치로
돌아오는 동작을 반대 스와이프로 오판하던 버그를 "정리 중(settling)" 상태로
고쳤다(손이 실제로 멈춰야 다음 판정을 연다). 손가락 모양(Fist/Palm) 기반 안은
MediaPipe Hands 모델이 있어야 해서 성능 실측 없이는 보류
(`play-zera-gesture-control-ux-spec.md` 참고, `docs/04` STEP 21).

`main`은 커밋까지 돼 있고 **푸시는 ken이 직접 한다**(맥 키체인에 인증이 있다).

**레일 스와이프 — 끝에 닿기만 해도 자동으로 넘어가던 버그 수정(STEP 23~24).**
1차: `core/edgeSwipe.js`가 무장 순간의 위치를 고정 anchor로 쓰던 걸 롤링 시간 창
(`windowMs` 기본 400ms)으로 바꿨다. 고정 anchor는 시간 제한이 없어서 손을
가만히 대고만 있어도 떨림이 수 초에 걸쳐 쌓여 문턱(3.5%)을 넘었다. ken이
"오른쪽은 이제 완벽한데 왼쪽에서는 여전히(스와이프 동작 없이) 넘어간다"고
재보고 — 몸을 가로질러 반대쪽 끝까지 손을 뻗을 때 도착 직후 관성으로
되튀는 동작이 롤링 윈도우만으로는 진짜 당기기와 구별이 안 됐다(위치만
보면 모양이 같다). 무장 직후 `armGraceMs`(정착 유예, 기본 200ms) 동안은
기준점을 계속 지금 자리로 옮겨 이 되튐을 흡수하도록 추가했다 — 예전
`swipeGate.js`의 "정리 중(settling)" 상태와 같은 발상. node 시뮬레이션으로
되튐을 흉내 내 150ms는 부족하고 200ms면 흡수되는 걸 확인했다(가정한
수치라 실기기 확인은 아직 안 됐다). `test/edgeSwipe.test.js` 17건.

**홈 화면 히어로 오른쪽 정리(STEP 23).** 게임 썸네일(`#pz-hero-poster`, 레일에도
같은 그림이 있어 중복)과 캐릭터 버튼(`#pz-buddy`)을 홈에서 없앴다. 그 자리에
손 컨트롤 카메라 미리보기(`#pz-hand-pip`)를 `:has()`로 옮겨 붙였다(1101px 이상
너비에서만 — 좁은 화면은 원래도 그 자리가 없었다). 캐릭터 접근은 `/me`(마이페이지)
버디 카드 오른쪽 위에 텍스트 버튼("내 친구 크게 보기 →")으로 옮겼다 — 일단
텍스트 버튼 하나로 자리만 만들었다.

**쥬라기 대탐험(3D)에 스토리텔링 뼈대 추가(STEP 26).** 인트로(엄마 공룡이
구조 부탁) · 레벨 3 완료 시 발견 장면(아기 공룡을 찾음, 이때부터 백팩에
말풍선으로 업고 감) · 엔딩 귀환 장면, 세 대화 화면을 `manifest.story`로
연결했다. 기존 장애물·레벨·조작은 하나도 안 건드렸고, 다른 러너3D 테마도
이 필드가 없어 영향 없다. 인트로·발견·엔딩 세 장면 모두 ken이 만든 합성 그림(인물+배경 한 장)으로
적용 완료, **소년/소녀 버전 둘 다** 있고(`playerSkin()`으로 자동 선택),
캐릭터별 표정 얼굴(엄마 걱정·기쁨, 소년·소녀 각 기본/걱정/기쁨)도 대사
내용에 맞춰 붙었다. 백팩 말풍선 그림(`story_baby_bubble.png`)도 받아
붙여서 **필요한 그림이 전부 채워졌다.** 대화창은 어두운 덮개를 뺐고,
이전 버튼 + 자동 넘김 타이머, 화면 자체가 항상 불투명하도록(로딩 중
이전 화면이 비쳐 보이던 버그 수정 — `readyScreen.js`가 자기 DOM을 안
지우던 게 원인이었다) 고쳤다. 덮개를 빼면서 배경 그림 연결(`var(--bg)`)
줄까지 같이 지워 잠깐 배경이 통째로 안 보이는 회귀가 났었는데 바로
잡았다(`docs/04` STEP 26).

**스토리 화면에 연출 4종 추가.** 인트로·발견(아기 공룡을 찾는 순간)
장면은 배경만 작게 계속 흔들고(대사창·버튼은 안 흔든다 — 손 제스처
조준이 깨지면 안 된다) 연기를 흘리고 폭발음을 낸다. 엔딩은 꽃가루
(`core/confetti.js` 재사용) + 폭죽음 + 귀여운 성공 배경음악. 대사가
넘어갈 때마다 짧은 효과음, 텍스트는 타이핑 효과로 나온다. 새 소리
파일은 안 만들었다 — 판정음(`playMissBuzz` 등)과 같은 방식으로
Web Audio API 합성이다(`runner/audio.js`).

**인트로 화면 오른쪽 위 버튼을 Home → 뒤로가기로 바꿨다.** 튜토리얼
둘째 장으로 실제로 돌아간다(글자만 바꾼 게 아니다) — `showTutorial3d`에
`startPage` 옵션을 추가하고, `play3d.js`의 튜토리얼 루프를 한 겹 더
감쌌다. 발견·엔딩 화면은 그대로 Home이다(운동 기록이 걸려 있어 "전
단계"가 없다). 폭발음도 크랙+흩어져 터지는 쿵 2~3번+천둥 rumble로
다시 짜고 볼륨을 키웠다.

**인트로가 장면 하나에서 넷으로 늘었다.** 평온 → 지진 시작(흔들림) →
화산 대폭발(기존 그림 재사용) → 아이의 다짐(클로즈업), 이 순서로
`story.intro.scenes` 배열이다. 장면 사이도 "뒤로"로 오갈 수 있고, 첫
장면에서 더 뒤로 가면 튜토리얼 둘째 장으로 돌아간다. 마지막 장면에는
게임이 곧 시작된다는 신호음(`playGameStart`)이 붙는다. 새 장면 그림
셋 중 소녀 버전은 아직 없다 — 있으면 좋음(선택), 급하진 않다.

**스킵 버튼 + 그림 둘 더 교체.** 인트로 화면 오른쪽 위에 "스킵"이
따로 있다(이전·다음과 안 묶었다) — 누르면 마지막 장면(다짐, 게임
시작 신호음 있는 곳) 하나만 보고 판이 시작된다. 게임 배경 하늘
그림(`bg_sky.png`)과 인트로 앞 두 장면(평온·흔들림) 그림을 더 나은
버전으로 바꿨다. **작업 폴더에 한 번 쓴 파일은 덮어쓰기가 막힐 수
있다는 걸 이번에 배웠다** — `story_scene_intro_calm/_tremor.png`는
덮어쓰기가 거부돼서 `_v2.png`로 새로 저장하고 manifest 경로만
바꿨다(옛 파일은 안 지워지고 남아 있다, 아무도 안 가리킨다).

**출발 대사 + 스킵 자리 이동 + 연기 색 + 모바일 접속.** 인트로 마지막
장면에 소년의 출발 대사("좋아, 가자! 출발!")를 추가했다. 스킵 버튼은
대화창 안 이전·다음 옆으로 옮겼고(같은 스타일), 이제 스킵을 누르면
**마지막 장면의 마지막 줄**(방금 그 출발 대사)로 곧장 간다. 화산
연기(게임 화면)는 흰색에서 짙은 잿빛으로 바꿨다. `vite.config.js`에
`server: { host: true }`를 추가해서 `npm run dev`를 다시 켜면 같은
와이파이의 휴대폰에서도 열린다 — 단, 카메라는 HTTPS가 아니면 iOS
Safari가 안 열어 준다(`docs/STEP9`), 레이아웃·키보드 모드 확인용이다.

**스토리 화면 나가기 버튼 + 엔딩 두 장면화 + 여자 버전 이미지.** 스토리
화면(인트로·발견·엔딩)에 나가기(X) 버튼이 추가됐다 — 누르면 게임
자체의 처음(`location.reload()`)으로 돌아간다. 인트로 마지막 장면은
스킵 대신 "시작" 버튼이 뜬다(자동 넘김은 그대로). 엔딩이 장면 하나
(엄마의 감사 인사)에서 둘(+ 새 그림 · 소년의 작별 인사 + 폭죽·꽃가루)로
늘었고, 모든 미션을 다 깨면 결과 화면("한 번 더" 버튼) 대신 곧장
게임 처음으로 되돌아간다 — 목숨이 다해 끝난 판은 그대로 결과 화면을
본다. 소녀 버전 이미지 5장(인트로 평온·흔들림, 엔딩 둘)을 마저 채워
인트로 4장면·발견 2장면·엔딩 2장면 전부 소년/소녀 버전이 다 있다.

**포즈 사인판 좌우 양방향(STEP 27).** 런지·옆구리늘리기(상체숙이기) 사인판이
늘 한쪽 방향으로만 나왔다 — 채점(`poseMatch.js`)은 원래 아이가 어느 쪽으로
해도 통과시켰지만, 그림이 한쪽뿐이니 아이는 반대쪽을 할 생각을 못 했다.
이제 나올 때마다(레벨 번호로 시작값을 갈라 레벨끼리도 다르게) 번갈아
뒤집혀 나온다 — 장애물 개수·간격은 그대로다. 캐릭터도 사인판 방향에
맞춰 반전해서 보여주고, **카메라로 아이가 실제로 반대쪽을 하면 캐릭터가
그쪽을 따라간다**(포즈 채점이 이미 알고 있던 "어느 쪽으로 맞았나"를
그대로 넘긴다). 팔벌리기는 좌우 대칭이라 안 건드렸다.

**자동재생(auto-play) 모드(STEP 28).** 카메라도 키보드·터치도 안 쓰고
"영상처럼" 캐릭터가 알아서 다 피해서 무조건 클리어되는 모드. 카메라
준비 화면에 "자율주행 모드" 버튼을 새로 추가했다(`allowAuto` 옵션 —
기본 꺼짐, 쥬라기 대탐험 3D만 켬. 다른 게임은 자동조종을 아직 안
구현해서 버튼 자체가 안 보인다). 코스를 미리 아는 스크립트
(`runner/game/autopilot.js`, 2D·3D 공용)가 저수준 컨트롤만 직접 불러서
운동 기록(EXP·배지)은 하나도 안 쌓이고, 서버에는 재생했다는 기록만
남는다(`input_mode: 'auto'`). 다섯 레벨 전부 한 번도 안 맞고 끝까지
가는지 실제로 굴려서 확인했다(`test/autopilot.test.js`). 사인판 좌우
반전(STEP 27)도 자동재생에서 그대로 따라간다. 작업 중 템플릿 문자열
안 CSS 주석에 백틱을 또 썼다가(`readyScreen.js`) `test/sourceParses.test.js`가
잡아서 고쳤다 — CLAUDE.md에 이미 적힌 패턴을 일곱 번째로 겪었다.

**자동재생 다듬기 + 버튼 이름(STEP 29).** ken이 실기기로 자동재생을 직접
보고 넷을 짚었다. 큐브를 피한 뒤 일정 시간(0.5초)이 지나면 가운데
레인으로 돌아오게 했다(심리적 안정감) — 연달아 나오면 마지막 것만
기준으로 한 번만 돌아간다. 포즈 LEAD를 0.15초 → 1.5초로 늘려 벽에 닿기
직전이 아니라 한참 전부터 자세를 잡게 했다(실제 사용자도 미리 잡는
것과 맞춘다). 큐브 회피가 가끔 가운데를 건너뛰고 반대편까지 두 칸을
한 번에 움직이던 버그도 고쳤다(`assignCubeLane`이 인접한 한 칸만
고르도록 제한). 버튼 이름도 "자동으로 보기"→"자율주행 모드",
"키보드로 하기"→"키보드 모드"로 바꿔 둘 다 "무엇으로 조작하나"를
뜻하게 맞췄다.

**스토리 이전 버튼 컷 경계 버그(STEP 30-①).** 인트로·발견·엔딩은 여러

`approachSec`은 안 건드린다). localStorage에 남아 다음에도 유지된다.
작업 중 CSS 주석 백틱 버그를 두 번 더 냈다(이번 세션만 세 번째) —
`test/sourceParses.test.js`가 매번 잡았다.

**매우 빠르게 대폭 상향 + 배속 버그 두 개(STEP 31).** ken이 "매우
빠르게가 너무 느리다, 장애물이 다가오는 속도가 엄청 빨랐으면 좋겠다"고

장애물만 빨리 다가오는 어긋남이 있었다(`view.course.speed`로 수정).
② 판정 창(`atHit`)이 배속에 반비례해 좁아져서, 배율을 올릴수록 반응
속도 시험이 될 뻔했다 — `hitWindow`를 배속과 같은 비율로 넓혀 **실제
초 단위 여유는 배속과 무관하게 그대로**이도록 고쳤다(`buildCourse3d`).

**실기기 검증 전**이다 — 어지러움·체감 난이도는 몸으로 해봐야 안다.

**바다 셰이더 축 버그 발견 + 입체감 재설계(STEP 35).** ken이 `#/lab-sea`를

시 블라인드로 보이던 원인 중 하나)에서 방향 없는 얼룩 무늬로 바꿨다.

**부표 경계물 추가(STEP 36).** ken이 물 확인 직후 이어서 요청 — 육지
러너는 연석(턱 있는 상자)으로 트랙과 잔디를 가르는데, 바다에도 "레인
바깥은 열린 바다"를 표시할 것이 있어야 한다고. ken 제안대로 부표로

로직을 짜지 않았다. `PropRow`에 `bob`(까딱임) 옵션을 새로 추가했다
(기본값 없음 = 육지 프롭은 그대로, 물에 뜬 것만 켠다) — 물건마다 x·z에서
위상을 뽑아 흔들어서 부표 전부가 같은 박자로 까딱이지 않는다(`DinoRow`가
공룡 위상을 흩뜨리는 것과 같은 이유). 부표 자체는 원기둥 셋+구 하나를

색을 구워(빨강/흰색 몸통 + 회색 기둥 + 주황 꼭대기 표식) draw call

   "인어 180° · 신상 180°"로 STEP 41의 기본값 그대로였다)에서 찍은
   것이라, `Math.PI`가 여전히 틀렸다는 것만 다시 확인됐다 — `0`도
   `π`도 이미 틀렸다고 확인된 두 후보다. 세 번째 숫자를 또 추측해서

   "이게 정답이다"가 아니라 "π에서 되돌리는 12번의 키 입력을 아끼는"

세 번째 요청(카메라에 여러 사람이 잡혀 다른 사람이 메인으로 인식되는
문제)은 ken이 "바로 작업 들어가지 말고 계획을 세우고 대화로 정한
다음에 진행하자"고 해서, 원인 조사(`MediaPipe numPoses:1` — 한
프레임에 몸 하나만 감지, 여럿 있으면 모델이 "가장 두드러진" 사람을
고르는데 그 기준이 "아이"를 보장 안 함)만 하고 대안을 상의했다 —
구현은 STEP 63으로 이어졌다.

**QR 스캔 버튼 — 이미 연결된 기기엔 숨김(STEP 72), 배포 진행.** 배포
직전 ken이 마지막으로 짚었다 — 이미 리모컨과 붙어 있는 기기가 "QR
스캔하기" 버튼을 또 볼 이유가 없다. `pairingModal.js`의 `render(state)`가
`state.connected`일 때 그 버튼과 "또는" 구분선에 `hidden`을 걸도록
두 줄만 고쳤다(연결 안 된 기기에서만 보인다). 테스트 874건 그대로
통과·빌드 통과. 이걸 끝으로 ken이 `main`을 배포한다 — STEP 68~71
(QR 스캔·카메라 오류 메시지·화면 미러링)의 실기기 검증은 이 배포
이후 HTTPS 주소에서 처음 이뤄진다.

**배포 전 화면 미러링 되살림(STEP 71).** ken이 STEP 70 설명을 확인한
직후 바로 요청 — "배포 전에 미러링까지 적용하면 안돼?" STEP 65에서
만들고 STEP 66(리모컨 전용 화면을 없애면서 "놓을 자리가 없다"는 이유로)
꺼 뒀던 화면 미러링을 다시 켰다. 이번엔 자리가 있다 — QR 팝업의 "조종
중" 패널(`pairingModal.js`의 `openControllerPanel`)에 "화면 보기" 토글
버튼과 video를 얹었다. 신호 보내는 쪽(`session.js`, 주 디바이스)은
STEP 65 코드 그대로 두고, 받는 쪽(`controller.js`, 리모컨)에 offer/
answer/ICE 처리와 `requestMirror()`/`stopMirror()`를 새로 짰다. 패널을
닫으면 켜져 있던 미러링도 같이 끈다(계속 떠 있는 화면이 아니라서, 안
그러면 아무도 안 보는데 인코딩만 도는 STEP 65의 걱정이 재현된다).
테스트를 쓰다가 진짜 버그 하나를 잡았다 — `_teardownMirror()`가 정리할
pc가 없을 때도 UI에 `null`을 알려서, 처음 화면을 받는 중인데 "끊겼음"
신호가 먼저 뜨는 문제였다(정리할 pc가 실제로 있었을 때만 알리도록
고쳤다). 테스트 874건(기존 867+신규 7) 전부 통과·빌드 통과. **미러링
영상이 실제로 뜨는지는 STEP 65 때부터 한 번도 실기기로 확인된 적 없다**
— QR 스캔·손 컨트롤과 마찬가지로 HTTPS 배포 주소나 터널이 있어야
테스트할 수 있다.

**카메라 연결 실패 진짜 원인(STEP 70).** ken이 정확한 오류 문구를
보내줬다 — "TypeError undefined is not an object (evaluating
'navigator.mediaDevices.getUserMedia')", 주소는 `192.168.219.103:5173`
(평문 HTTP, IP 접속). STEP 69의 두 수정(facingMode 폴백·video.play())은
틀린 추측이었다 — **진짜 원인은 안전한 컨텍스트(HTTPS·localhost)가
아니면 `navigator.mediaDevices` 자체가 없다는 것**, `docs/STEP9`에
이미 적힌 "아이폰은 HTTPS라야 카메라가 열려요" 제약을 새 기능(QR
스캔)에서 다시 만난 것이다(손 컨트롤은 같은 상황에서 버튼이 조용히
숨어서 안 보였을 뿐). JS로 우회할 방법이 없는 브라우저 보안 정책이라
**문구만 고쳤다** — raw TypeError 대신 `handControl.js`에 이미 있는
`SecurityError: 'HTTPS에서만 쓸 수 있어요'`로 뜨게 했다. **카메라가
걸린 기능은 배포된 HTTPS 주소나 로컬 HTTPS 터널로만 실기기 검증
가능** — QR 페어링 자체(카메라 없는 부분)는 평문 HTTP에서도 계속
잘 된다. 테스트 867건 그대로 통과·빌드 통과.

**QR 스캐너 버튼 강조 + 카메라 연결 버그 수정(STEP 69).** ken이 재테스트
— "버튼이 눈에 띄지 않아, 크기 키우고 강조한 컬러로" + "카메라 연결이
안돼." 버튼을 밑줄 링크에서 그라데이션(`#0ECAFD→#0057EC`, 속도 버튼과
같은 액센트) 꽉 찬 버튼으로 바꿨다. 카메라 연결 버그는 실기기 콘솔
없이 코드로 가장 그럴듯한 원인 둘을 고쳤다 — `facingMode:'environment'`를
맨값으로 줘서 일부 기기가 `OverconstrainedError`로 완전히 실패했을 것
(→ `ideal`로 바꾸고 실패하면 카메라 아무거나로 재시도하는 `openCamera()`
추가), `video.srcObject`만 걸고 재생을 명시적으로 안 시켰을 것(→
`video.play()` 추가). 테스트 867건 그대로 통과·빌드 통과. **다음
재테스트에서 화면에 뜨는 정확한 오류 문구를 봐야 진짜 원인인지
확정된다.**

**부모 리모컨 — 팝업 안에서 QR 스캔하기(STEP 68).** ken이 "홈화면에서도
qr코드 촬영할 수 있게 카메라 연결하는 버튼" 추가를 요청 — 지금까지는
폰의 OS 카메라 앱으로만 QR을 스캔할 수 있었다. `BarcodeDetector`
네이티브 API는 iOS Safari가 2026년에도 전혀 구현 안 해서(검색으로
확인, `getDisplayMedia`와 같은 종류의 함정) 대신 순수 JS 디코더
`jsqr`을 새로 설치했다. ken이 지정한 대로 QR 아이콘 팝업 안에 "대신
QR 스캔하기" 링크를 추가 — 누르면 모달이 카메라 스캐너 화면으로
바뀌고, 후면 카메라로 다른 화면의 QR을 찍어 디코드되면
`#/remote?code=...`로 이동시켜 기존 `remote.js` 흐름을 그대로
이어받는다(연결 로직 중복 없음). 새 순수 함수 파일
`core/remote/qrUtil.js`(테스트 때문에 분리 — `pairingModal.js`는
포즈 엔진까지 물고 있어 무겁다). 테스트 867건(기존 861+신규 6) 전부
통과·빌드 통과, `jsqr`는 별도 청크로 분리돼 스캔 버튼을 누를 때만
받는다.

**부모 리모컨 — 연결 실패 막다른 화면 수정(STEP 67).** STEP 66을
실기기로 재테스트한 ken이 "연결 잘 돼"로 확인하면서 새 버그를 짚었다
— 연결이 지연돼 결국 시간 초과가 나면 "다시 시도해 주세요" 문구만
뜨고 멈춰서 버그처럼 보인다고. `remote.js`의 코드 없음·거부·시간 초과
세 경우 전부 `renderDeadEnd()`로 교체 — 4초 뒤 스스로 허브로 돌아가고,
"홈으로" 버튼도 같이 뒀다(ken이 "둘 다 가능하면 더 좋고"). 화면 미러링은
여전히 STEP 66대로 빠진 상태(코드는 남아 있음). 테스트 861건 그대로
통과·빌드 통과.

**부모 리모컨 — 실기기 피드백 반영(STEP 66).** ken이 아이폰(리모컨)+
아이패드(주 디바이스)로 STEP 64~65를 실제로 테스트하고 넷을 지적했다
— 리모컨 전용 화면 디자인이 별로다, QR 팝업이 연결 후에도 안 닫힌다,
**리모컨 화면은 전용 UI가 아니라 진짜 허브 그대로여야 한다**, QR
아이콘에 연결 표시(빨간 펄스)가 있어야 한다. 가장 큰 변화는 셋째다 —
전용 리모컨 페이지를 없애고, `router.js`의 `navigate()` 하나만
가로챘다. 허브 히어로 버튼도 게임 Home 버튼도 결국 이 함수를 부르므로,
리모컨(폰)이 "조종 중"일 때 이 함수가 로컬 이동 대신 명령만 보내면
허브·게임 코드는 한 줄도 안 고치고 "플랫폼 그대로 조종"이 된다. 새
싱글톤 `core/remote/controller.js`(리모컨 쪽, `session.js`의 반대편) +
`remote.js`는 승인만 받는 부팅 화면으로 축소(승인되면 `location.hash
= '/'`로 진짜 허브를 띄운다) + `pairingModal.js`는 연결 순간 스스로
닫히고 역할(주 디바이스/조종 중)에 따라 다른 패널을 연다 +
`bindRemoteButton.js`(신규)가 QR 아이콘의 빨간 펄스를 담당. 명령
프로토콜도 `start`/`stop` 둘에서 `{type:'navigate', path}` 하나로
단순해졌다. **화면 미러링("화면 보기")은 이번엔 뺐다** — 리모컨이
허브에 머무르므로 비출 게임 화면 자리가 없어졌다, ken 확인 "일단
빼기"(코드는 안 지움). 새 테스트 14건(controller.js 10건 + session.js
연결끊기 알림 4건) — 861건 전부 통과·빌드 통과. **navigate() 가로채기가
실제 브라우저에서 도는지 전부 실기기 미검증.**

**부모 리모컨 2단계 — 화면 미러링(STEP 65).** "다음 단계까지 진행하자"는
ken 지시로 바로 구현하기 전에 가정부터 검산했다 — `canvas.captureStream()`은
게임 캔버스(세계·캐릭터)만 잡고 그 위 HUD(DOM)는 안 잡힌다는 것, 캔버스가
아예 없는 순수 DOM 게임(불 끄기·돌다리·팝팝 클리커, 전부 `status:hidden`)은
이 방식으론 못 비춘다는 것, `getDisplayMedia`(화면 공유)는 대안이
아니라는 것(2026년 현재도 아이폰·안드로이드 모바일 브라우저 전부
미지원, 데스크톱 전용 API)을 확인했다. 지금 노출된 세 게임은 전부
캔버스 기반이라 실사용엔 지장 없어 — 범위를 "게임 세계만"(HUD 숫자는
다음)으로 좁혀 진행했다. `session.js`에 `mirror-request`/`mirror-stop`/
`webrtc-answer`/`webrtc-ice` 신호(같은 Realtime 채널 재사용, TURN 없이
STUN만) + 화면 전환마다 캔버스를 다시 찾아 연결을 갈아 끼우는
`_reconcileMirror()` 추가. 리모컨(`remote.js`)엔 "화면 보기" 토글 +
video 엘리먼트. 자동으로 안 켜진다 — 리모컨이 눌러야 인코딩이
시작된다(성능 예민, `#/lab3d`와 같은 이유). 가짜 `RTCPeerConnection`으로
신호 흐름 10건 신규 테스트 — 846건 전부 통과·빌드 통과. **영상이
실제로 뜨는지·지연·FPS 영향은 전부 실기기 미검증.**

**부모 리모컨 1단계 — QR 페어링 + 켜고끄기/게임고르기(STEP 64).** 다인
카메라 다음 지시대로 리모컨(부모 폰) 설계 대화를 먼저 하고 구현했다.
범위는 켜고 끄기+게임 고르기까지(실시간 3D 화면 미러링은 2단계로
미룸). 페어링은 QR — 열 때마다 새 코드로 새 채널을 만들고(고정 QR
아님) 주 디바이스가 매번 승인해야 붙는다("화면을 봐야 스캔할 수
있다"는 물리적 제약이 보안 경계다, Realtime 자체는 "같은 와이파이"를
강제 못 함). 새 싱글톤 `core/remote/session.js`(주 디바이스, 페이지를
넘나들어도 산다) + `pairingModal.js`(홈의 QR 아이콘, `qrcode` 패키지
신규 설치, 동적 import) + `src/pages/remote.js`(폰 쪽, 손 커서 없음,
게임 고르고 "시작"을 눌러야 명령이 나간다 — 허브의 "고르기/실행 분리"
규칙과 같음). 명령은 `start`{gameId}·`stop` 둘뿐이다. `test/remoteSession.test.js`
15건 신규(가짜 채널로 승인 흐름·명령 처리 확인, 실제 네트워크는
실기기 필요) — 836건 전부 통과·빌드 통과. `npm run check`의 에셋
예산 실패는 이번 작업과 무관(이전부터 있던 것, `git stash`로 확인).
**QR 스캔→페어링 전체 흐름·아이패드 사파리 렌더링 전부 실기기 미검증.**
2단계(WebRTC 영상 미러링, `canvas.captureStream()` 방향으로 설계만
됨, TURN 서버 없이 시작하기로 함)는 다음 세션.

**다인 카메라 인식 — 두 단계 잠금 방식으로 구현(STEP 63).** 여러 턴에
걸친 설계 대화 끝에(① 미래 회원 얼굴 인식 기능과 자리를 맞출 것,
② "가운데 우선"이 2인 이상일 땐 애매해진다는 지적) 두 단계로
정리했다 — **잠기기 전**은 매 프레임 중앙·크기·**O자세 시도 중이면
압도적 가산점**으로 점수를 매겨 고르고(모든 게임이 이미 요구하는
시작 동작이라 아이에게 새로 시키는 게 없다), **잠긴 뒤**는 위치
연속성으로만 따라간다(유예 시간 있음). 잠그는 시점은 화면이 정한다
— 카메라 준비 화면이 O자세 성공/이어서 하기 순간에 `confirmLock()`을
부른다. 새 모듈 `core/pose/personLock.js`(순수 함수, 향후 얼굴 인식
스코어러를 갈아 끼울 수 있게 점수 함수를 분리해 둠), `poseEngine.js`는
`numPoses: 1→2` + 매 프레임 후보 중 하나를 골라 기존처럼 "한 사람"만
구독자에게 넘긴다. `readyScreen.js`의 `finish('motion')` 한 곳에
`confirmLock()` 연결. 새 테스트 13건(`personLock.test.js`) — 818건
전부 통과·빌드 통과. **`TRACK_LOSE_GRACE_SEC`(2.5초)·`TRACK_MATCH_DIST`
(0.30)·`numPoses: 2`의 FPS 영향은 전부 실기기 미검증**이다.

적당한지), 두 기기 QR 아이콘 모두 펄스가 잘 보이는지, "연결 끊기"가
양쪽에서 다 되는지를 봐야 한다. TURN 서버 없이 시작했으므로 두 기기가
직접 못 붙는 네트워크(대칭 NAT 등)에서 얼마나 자주 실패하는지도
실기기로 봐야 TURN을 붙일지 정할 수 있다.

**부모 리모컨 — 화면 보기(게임 플레이 실시간 영상)는 뺀 상태다.**
STEP 65에서 만든 `canvas.captureStream()` 미러링 코드는 `session.js`에
그대로 남아 있지만 어디서도 안 부른다 — 리모컨이 이제 허브에 머무르며
비출 게임 화면이 없어졌다. 위 실기기 확인이 끝나고 "게임 플레이를
실시간으로 보고 싶다"는 필요가 실제로 있으면, 연결 상태 패널에 버튼
하나를 놓는 안부터 검토한다.

**다인 카메라 인식(STEP 63) — 실기기로 확인한다.** `numPoses: 2`의
FPS 영향, 유예 시간(2.5초)·매칭 거리(0.30)가 실제 보호자 개입 상황에서
적절한지, O자세 가산점이 실제로 "가운데 선 보호자보다 구석의 아이"를
이기는지 — 전부 아이패드로 직접 확인이 필요하다.

**쥬라기 대탐험(3D) 스토리 화면 — STEP 61 세 가지를 실기기(아이패드)로
다시 확인한다.** 스킵이 이제 정말 화면 없이 곧장 시작되는지, 첫
장면에서도 캐릭터 얼굴이 뜨는지, 이전·다음/스킵이 갈라진 배치가
손 제스처·터치 둘 다에서 자연스러운지.

**`#/lab` 또는 실기기에서 STEP 60의 칸 폭 값을 직접 확인한다.**
`LANE_STEP`(0.24)·바닥값(0.10)은 이 세션에서 계산으로만 고른
값이라 아직 실기기 미검증이다 — 아이가 실제로 움직여 보고 "여전히
넓다" 쪽인지 "이제 너무 예민하다" 쪽인지 봐야 한다. `laneThreshold`
자체는 러너에서 검증된 값이지만 여기선 의미(문턱→칸 폭)를 다르게
써서 그대로 안전하다고 볼 수 없다. 괜찮으면 미뤄 둔 PIP 오버레이의
등분선(화면 표시가 실제 경계보다 넓게 그려지는 것)도 같이 손볼지
정한다.

**`npm run dev` → `#/lab-island`·`#/lab-ithaca`·`#/lab-sea` 전부 열어서
최근 결과를 눈으로 본다.** 렌더링 자체는 스크린샷으로 확인됐지만,
톤·배치·FPS·타이밍 같은 세세한 검수는 아직이다. (이 세션의 인앱
브라우저는 `document.hidden`이 항상 `true`라 `requestAnimationFrame`이
억제돼 실시간 체감·FPS 실측이 안 된다 — 실제 브라우저 탭에서 봐야
한다. `#/lab-sea`는 이번에 rAF 오버라이드로 우회해서 봤지만, 그건
로직 확인용이지 "체감이 자연스러운가"의 답은 아니다.)

`#/lab-sea`: 정적 스크린샷으로는 확인됐지만(STEP 59) **실시간 체감은
아직**이다 — 번개 다리의 높이(3.4유닛)·처짐(0.9유닛)·크래클 속도가
`npm run dev`로 실제로 봤을 때도 자연스러운지, 소용돌이의 `WHIRL_Y`
(0.32)가 너무 떠 보이지 않는지 가장 먼저 확인한다. 그다음 새 입체
소용돌이(STEP 57)가 그림과 얼마나 비슷한지, 부풀어 오른 테두리
높이·빙빙 도는 속도·안으로 빨려드는 속도가 적당한지, 스페이스바
점프 타이밍이 아이에게 자연스러운지(예고 신호가 아직 없다), 배 점프
높이(2.2유닛)가 과하거나 부족하지 않은지. 신상 각도가 345도(STEP
58)로 실제로 정면인지도 같이 확인한다. 노 젓는 캐릭터 빌보드가
배·소용돌이·주변 프롭과 크기 비례가 맞는지, 노 젓는 속도(초당
2.2회)가 자연스러운지 — girl 스킨 그림이 오면
`boat_char/girl/row_up.png`·`row_pull.png`로 넣어 붙인다. 이 화면은
완전히 무음이다(STEP 55·56) — 허전하면 다른 소리를 고른다.

`#/lab-island`: 거인이 커진 게 자연스러운지, 인어를 뺀 자리가
허전해 보이는지(배·록키 템플·신상 셋만으로 층이 부족해 보이면 다른
걸 채워야 할 수 있다).

`#/lab-ithaca`: 원본 하늘 그림이 사막 팔레트 위에서 자연스러운지,
기사·개·염소·방패+돌이 서로 겹치지 않는지, 나무 실루엣(정이십면체
두 뭉치)이 진짜 나무처럼 읽히는지, 30그루씩이 "숲"처럼 느껴지는지,
록키 템플이 사막 스테이지에도 어울리는지, 기사·여신상 A·여신상 B·
목마가 아직 0도 기본값이라 등이 보일 수 있다(화면의 "방향 맞추기"
카드에서 Tab으로 고르고 ,/.로 15도씩 돌려 정면을 찾는다 — STEP 44에서
인어·신상을 찾은 것과 같은 방식). 실제 FPS도 이번에 처음 재는 것이다.

통과하면 다음은 기둥·황금 문 같은 나머지 그리스풍 배경물을 두
화면 모두에 마저 붙이는 단계다(콘셉트아트 기준). 이타카 전용
장애물도 그때 정해서 `obstacleVisual` 패턴으로 붙인다.

그 다음 STEP 40~45에서 쌓인 바다 구간 확인 항목도 마저 남아 있다 —
전부 Claude가 아직 눈으로 못 봤다.

1. **하늘 번개가 화면 플래시보다 나은가** — 지그재그 선이 실제로
   "전기 흐르듯" 보이는지, 위치·굵기·밝기가 적당한지. 너무 안 띄면
   `boltMat`의 `opacity`나 선 두께(three.js는 `linewidth`가 대부분
   브라우저에서 안 먹는다 — 굵게 하려면 선을 여러 겹 겹치거나
   `LineSegments2`(fat line)로 바꿔야 할 수 있다)를 조정한다. 이제
   소리 없이 시각 효과만이라(STEP 56) 그것만으로 "번개"로 읽히는지도
   같이 본다.
2. **드래곤이 커진 게 자연스러운가, 신상이 이제 좌우 둘 다 정면인가.**
3. **이 화면이 이제 완전히 무음인 게 허전하지 않은가** — 빗소리(STEP
   55)·번개 효과음(STEP 56)을 둘 다 뺐다. 필요하면 다른 소리를
   새로 골라 넣는다.
4. **fps가 버티는지** — 번개 선(간헐적, draw call 최대 2개)이 늘었다.

전부 괜찮으면 `runner3d/scene.js`·`backdrop.js`·`models.js`·`props.js`를
테마 데이터를 받게 뜯어고치는 리팩터로 넘어간다(`docs/04` STEP 34).

**`#/lab`에서 `row`(로우/노 젓기)도 실제 카메라로 확인한다.** 문턱값
(`pullOut`·`pullHysteresis`, `core/pose/detectors/row.js`)이 전부
눈대중이라 실제로 노 젓는 동작을 하면서 조정해야 한다.
