## 개정 요약 (v2 → v3)

| 항목 | v2 | v3 |
|---|---|---|
| 실행 주체 | 노트북 1대 단독 | **폰이 본체, TV는 미러링된 모니터** |
| 대상 환경 | 센터 중심 | **가정 + 센터 양쪽** |
| 조작 | O/X 제스처가 전부 | **목록=포인터 / 확인=O·X / 플레이=게임별 모션** 3층 분리 |
| 입력 수단 | 제스처 | **제스처 · 마우스 · 터치 3종 동등 지원** |
| 게임 분류 | category 필드 (구조) | **tags 기반 필터 (구조 아님)** |
| 홈 화면 | 사이드바 + 그리드 | **사이드바 제거, 이어서 하기 + 전체 게임** |
| 보조 기기 | 없음 | **보조 컨트롤러 폰 (완전 선택)** |

**v2에서 무엇이 틀렸나** — v2는 "멀티디바이스가 복잡하니 노트북 1대로"라고 정리했다. 방향은 맞았지만 전제가 센터 환경이었다. 가정에서는 노트북을 TV에 연결해 쓰는 집이 드물고, 웹 되는 TV라도 **TV에는 카메라가 없다.** 결국 폰이 필요하다. 그렇다면 폰을 카메라로만 쓸 게 아니라 **폰이 전부 다 하게** 하는 것이 맞다.

## 1. 프로젝트 개요

### 비전
AI 모션인식 기반 유아체육 게임 **허브 플랫폼**.
아이들이 몸을 움직여 게임을 즐기고, 그 움직임이 곧 조작이 되며, 그 결과가 **운동 데이터로 누적되어 성장 리포트로 연결**된다.

### 3개의 축

```
① 게임 허브        플레이 제라 = 게임팩이 꽂히는 플랫폼
② 몸으로 하는 조작  손 포인터 + O/X — 손에 아무것도 안 듦
③ 운동 데이터      플레이할수록 아이의 운동 기록이 쌓임
```

이 셋 중 **③ 운동 데이터가 플랫폼의 존재 이유**다. 게임은 데이터를 모으는 즐거운 수단이고, 허브는 그 게임들을 담는 그릇이며, 조작 체계는 아이가 도구 없이 참여하게 만드는 인터페이스다.

### 핵심 가치
- 아이들이 화면을 보고 **실제로 몸을 움직이게** 만드는 콘텐츠
- **손에 아무것도 들지 않고** 몸만으로 게임 전체를 조작
- **폰 하나만 있으면** 어디서든 시작 — 설치도, 기기 연결도, 계정도 없이
- 센터 수업 → 운동 데이터 누적 → 학부모 리포트 → 콘텐츠 사업으로 확장

### 파트너십
- **자파리센터**: 테스트베드 파트너, 유아 스포츠 교육 전문 센터
- **1차 테스트**: 2026년 7월 8일 완료
- **센터 코드**: ZAFARI2026

## 2. 실행 환경 ★ v3 핵심

### 발상: 폰이 본체, TV는 모니터

v1의 문제는 멀티디바이스라서가 아니라 **폰을 센서로만 쓰고 두뇌를 다른 기기에 뒀기 때문**이다. 매 프레임 포즈 데이터를 네트워크로 흘려보내야 했고, 세션 코드로 페어링해야 했고, 끊기면 게임이 죽었다.

폰이 전부 하면 이것이 통째로 사라진다.

```
[폰 하나가]  카메라 + MediaPipe + 게임로직 + 렌더링 + 터치조작
     ↓
   미러링 / HDMI 케이블
     ↓
[TV는]  화면만 띄움 — 스마트 TV든 구형 TV든 무관
```

페어링 없음. 세션 코드 없음. 네트워크 의존 없음.

### 왜 TV 브라우저를 쓰지 않는가

| 이유 | 내용 |
|---|---|
| 카메라 없음 | TV에는 내장 카메라가 없다 |
| USB 웹캠 미지원 | 삼성 Tizen 브라우저는 일반 카메라와 연동 불가 |
| 동작 불확실 | LG webOS는 같은 TV에서 앱마다 카메라 되고 안 되고가 갈림 |
| 성능 | TV 브라우저는 PC·모바일 대비 기능이 제한적 |

**웹 되는 TV든 안 되는 TV든 폰이 필요하다는 결론이 같다.** 그렇다면 TV 브라우저를 쓸 이유가 없다.

### 세팅 티어

| | 구성 | 페어링 | 지연 | 주 사용처 |
|---|---|---|---|---|
| **A** | 폰 + HDMI 케이블 → TV | ❌ | 없음 | 가정 (최적) |
| **B** | 폰 + 미러링(AirPlay/스마트뷰) → TV | ❌ | 100~200ms | 가정 (최다) |
| **C** | 폰·태블릿 단독 (거치만) | ❌ | 없음 | TV 없는 집, 여행 |
| **D** | 노트북·PC + USB 웹캠 | ❌ | 없음 | 자파리센터 |

**네 가지 모두 페어링이 없다.** 웹앱 하나가 그대로 돌아간다.

### 카메라 · 거리
- 권장 거리: 아이와 카메라 **1.5~2m**
- 폰은 **가로 거치** — 미러링 화면비가 맞고, 화각도 가로가 유리
- 다인 플레이 시 광각 필요 → 티어 D(외장 웹캠)가 유리

### 세팅 안내에 반드시 들어갈 것
- **충전 연결** — 카메라 + AI 인식 + 미러링 동시 구동은 발열·배터리 소모가 크다. 20분 수업이면 스로틀링이 온다.
- **가로 거치** — 세로로 두면 TV 화면이 좌우로 빈다.
- **거리 1.5~2m** — 앱이 자동으로 판정해 안내한다.

## 3. 조작 체계 ★

### 세 층으로 나눈다

> ⚠️ **v3 초판 정정** — 초판은 "메뉴=포인터 / 게임 중=O/X"로 기술했으나, 실제 구현된 웜업 게임(JAPARI RUN)은 그 반대다. `gestureRecognizer.js` 주석에 명시되어 있듯 **O/X는 메뉴·화면 전환용**이고, 게임플레이는 레인·점프·숙이기·포즈매칭을 쓴다. 실제 코드를 정본으로 아래와 같이 정정한다.

| 층 | 수단 | 쓰는 곳 | 상태 |
|---|---|---|---|
| **목록 선택** | 손 포인터 + 머무르기 | 홈의 게임 그리드 | 신규 개발 |
| **확인 · 전환** | O / X 유지 | 스타트, 준비, 종료 확인, 게임오버 | **이미 구현됨** |
| **게임플레이** | 게임별 모션 | 플레이 중 | **이미 구현됨** |

**선택지 개수가 기준이다.** 두세 개짜리 이지선다는 O/X로 충분하고 이미 잘 돌아간다. O/X로 풀 수 없는 것은 **선택지가 스무 개 넘는 게임 목록**뿐이다. 포인터는 정확히 그 구멍만 메운다.

이 구분 덕분에 게임팩은 자기 스타트 화면을 그대로 가질 수 있다. 스타트 화면의 선택지는 "시작/뒤로" 두 개뿐이므로 O/X면 되고, 포인터를 붙일 필요가 없다.

### 게임플레이 모션은 게임팩이 정한다

O/X를 모든 게임의 플레이 입력으로 강제하지 않는다. 게임마다 필요한 동작이 다르다.

| 게임 | 플레이 입력 |
|---|---|
| 웜업 장애물 (구현됨) | 레인 좌우 · 점프 · 숙이기 · 포즈 유지 |
| 똥 피하기 (개조 예정) | 미정 — 기획 확정 필요 |

manifest의 `gestures` 필드에 그 게임이 쓰는 입력을 선언하고, 허브는 선언된 detector만 활성화한다.

### 손 포인터 (게임 목록 전용)

손을 어깨 위로 들면 화면에 포인터가 뜨고, 손을 따라 움직인다. **버튼 위에 1.2초 머물면 클릭**된다. 링이 차오르는 것으로 진행 상황을 보여준다.

**왜 주먹 쥐기가 아니라 머무르기인가**

| | 주먹 클릭 | 머무르기 클릭 |
|---|---|---|
| 필요 모델 | Pose + **Hands 추가** | **Pose만** (손목 좌표) |
| 1.5~2m 거리 | 손이 화면의 5~8% → 손가락 판정 불안정 | 손목만 보면 됨 → 안정 |
| 폰 성능 | 모델 2개 = 부담 | **추가 비용 0** |
| 아이가 배울 것 | "주먹 쥐면 클릭" | **없음** |

주먹 클릭은 아이들 반응을 보고 "머무르기가 답답하다"는 피드백이 나올 때 옵션으로 추가한다. 처음부터 둘 다 넣으면 어느 쪽이 문제인지 구분이 안 된다.

**머무르기 시간은 되돌리기 난이도에 비례시킨다**

| 동작 | 시간 | 이유 |
|---|---|---|
| 스크롤 · 페이지 이동 | 0.5초 | 되돌리기 쉬움 |
| 카테고리 선택 | 0.6초 | 목록이 바뀌어 놀랄 수 있음 |
| 게임 시작 | 1.2초 | 잘못 누르면 게임이 시작됨 |

### O/X 제스처 (확인 · 화면 전환) — 이미 구현됨

| 제스처 | 동작 | 의미 |
|---|---|---|
| **O** | 양팔을 머리 위로 올려 동그라미 | 예 / 시작 / 계속 |
| **X** | 양팔을 교차 (가슴 앞 등 편한 위치) | 아니오 / 종료 / 뒤로 |

웜업 게임(`gestureRecognizer.js`)에 이미 구현되어 현장 검증까지 마쳤다. **이 코드가 정본**이며 `core`로 승격시킨다.

**구현된 판정 로직의 핵심**

- **O는 머리 위 유지를 요구, X는 요구하지 않는다.** X를 머리 위로 제한하면 플레이 중 인식이 잘 안 돼서 완화한 결과다.
- **X 판정은 상반신(어깨·손목)만 쓴다.** 전신(코~발목) 기준으로 하면 달리기·점프 중 발목이 프레임을 벗어나 인식이 깨진다. 정지 화면에선 잘 되는데 플레이 중엔 안 되던 문제의 원인이었다.
- **유지 시간은 상황별로 다르다.** 시작 3.0초 / 확인 1.5초 / 튜토리얼 건너뛰기 1.0초.
- **놓쳤을 때 즉시 리셋하지 않는다.** 누적의 60% 속도로 천천히 감소시킨다. 카메라가 한두 프레임만 흔들려도 처음부터 다시 해야 하면 "잘 안 된다"고 느낀다.

> 마지막 항목이 특히 중요하다. 손 포인터의 머무르기도 같은 방식으로 만들어야 한다. 이미 `GestureHold` 클래스가 `progress` 값을 제공하므로, **머무르기 링 UI는 사실상 이미 구현되어 있다.**

제스처 종류를 늘리는 데는 신중해야 한다. 종류가 늘수록 오인식이 늘고 아이가 좌절한다. **선택지가 많은 화면은 제스처가 아니라 포인터로 푼다**는 원칙이 이 때문이다.

### 입력 3종 동등 지원

같은 화면을 세 가지 방법으로 조작할 수 있다.

| 입력 | 포커스 | 실행 | 상황 |
|---|---|---|---|
| **손 포인터** | 손 위치 | 머무르기 | 아이가 떨어져서 플레이 |
| **마우스** | 호버 | **클릭 즉시** | PC·노트북 (티어 D) |
| **터치** | — | **탭 즉시** | 폰·태블릿 직접 조작 |

**머무르기는 손에만 적용한다.** 마우스 사용자에게 1.2초를 기다리게 하면 고장 난 줄 안다.

### 보조 컨트롤러 (선택)

손 포인터가 잘 안 될 때 다른 폰으로 접속해 리모컨처럼 쓸 수 있다. **단, 완전한 선택 사항이다.**

| | v1의 두 번째 기기 (폐기) | v3 보조 컨트롤러 |
|---|---|---|
| 역할 | 카메라 — 초당 30회 포즈 전송 | 리모컨 — 가끔 명령 하나 |
| 끊기면 | 게임이 죽음 | **아무 일 없음, 손으로 계속** |
| 필수 여부 | 필수 | **없어도 100% 동작** |

이 원칙을 지키는 한 보조 기기는 위험하지 않다. 어길 경우 v1의 실패를 반복한다.

## 4. 게임 허브 & 게임팩 구조

### 개념

```
        플레이 제라 (허브)
   ┌──────────────────────────────┐
   │  공통 엔진                   │
   │  · 포즈 인식 (MediaPipe)     │
   │  · 포인터 + 제스처 판정      │
   │  · 운동 데이터 기록          │
   │  · UI / 라우팅 / 디자인      │
   └──────────────────────────────┘
              ↑ 꽂힌다
   ┌────┬────┬────┬────┬────┬────┐
   │웜업│똥  │공룡│고양│냉장│로켓│  ← 게임팩
   └────┴────┴────┴────┴────┴────┘
```

폴더 하나 추가 = 허브에 자동 등록. 하드코딩 없음.

### manifest.json (v3)

```json
{
  "id": "warmup-obstacle",
  "title": "인터랙션 웜업 장애물 피하기",
  "description": "장애물을 O/X 동작으로 판단해 피하세요!",
  "thumbnail": "assets/thumb.png",
  "ageRange": "4-8",
  "players": { "min": 1, "max": 4 },
  "gestures": ["O", "X"],
  "tags": ["달리기", "순발력", "웜업"],
  "skills": ["순발력", "판단력"],
  "metrics": ["reactionAvgMs", "accuracy"],
  "rounds": 5,
  "status": "active",
  "createdAt": "2026-07-20"
}
```

**v2 대비 변경**
- `category` **삭제** → `tags` 배열로 대체
- `orientation` 삭제 (가로 고정)
- `thumbnail`, `createdAt` 추가 (NEW 배지 자동 판정용)

### 왜 카테고리가 아니라 태그인가

카테고리를 **구조**로 쓰면 게임마다 "이건 어느 칸에 넣지?"를 정해야 한다. 그 순간 분류가 게임 기획을 제약한다. 점프도 하고 협동도 하는 게임은 어디에 두는가? 양쪽에 넣으면 중복 노출되고, 한쪽만 넣으면 반대쪽에서 사라진다.

| | 카테고리 = 구조 | 태그 = 필터 |
|---|---|---|
| 게임의 위치 | 한 칸에만 존재 | 목록에 항상 있음 |
| 다중 분류 | 중복 노출 문제 | 자연스럽게 모두 걸림 |
| 개발할 때 | 칸에 맞춰 기획해야 함 | **만들고 나서 태그만 붙임** |

태그는 만든 게임에 나중에 라벨을 붙이는 것이라 개발을 제약하지 않는다. 홈 화면의 기본 상태는 "전체"이며, 필터는 선생님이 "오늘은 하체 위주로" 할 때 쓰는 도구다.

## 6. 운동 데이터 ★ 플랫폼 핵심

### 왜 핵심인가
게임은 하나씩 늘어나고 언젠가 유행이 지나지만, **아이의 운동 데이터는 사라지지 않고 계속 쌓인다.** 플레이 제라가 단순 게임 모음이 아니라 플랫폼인 이유가 여기 있다.

```
아이가 논다  →  움직임이 측정된다  →  데이터가 쌓인다
                                          ↓
                              가정: 우리 아이 성장 기록
                              센터: 수업 효과 근거
                              사업: 축적된 유아 운동 데이터셋
```

### 수집 지표

**공통 지표 (모든 게임팩 자동 수집)**

| 지표 | 산출 방식 |
|---|---|
| 플레이 시간 | 게임 세션 길이 |
| 동작 횟수 | 제스처 엔진 카운트 |
| 평균 반응속도 | 자극 → 동작 타임스탬프 차 |
| 정확도 | 성공 / 전체 시도 |
| 활동량 | 관절 변위 누적 (어깨 너비로 정규화) |

**게임별 지표** — manifest의 `metrics`에 선언된 항목만 추가 수집

### 역량 지표 (파생)

| 역량 | 산출 근거 |
|---|---|
| 순발력 | 평균 반응속도 |
| 민첩성 | 활동량 / 플레이 시간 |
| 집중력 | 후반 라운드 정확도 유지율 |
| 조절력 | HOLD·균형 계열 성공률 |
| 지구력 | 후반 활동량 유지율 (누적 데이터 필요) |

### ⚠️ 미러링 지연이 데이터를 오염시킨다

티어 B(미러링)는 화면이 100~200ms 늦게 표시된다. 아이는 늦은 화면을 보고 반응하므로 **측정된 반응속도에 그만큼이 얹힌다.**

운동 데이터가 이 플랫폼의 핵심인 이상 방치할 수 없다.

- 결과 저장 시 **세팅 티어(A/B/C/D)를 함께 기록**한다
- 게임 시작 전 **1회 지연 캘리브레이션**을 수행해 보정값을 구한다
- 원본 수치와 보정 수치를 **모두** 저장한다 (나중에 재계산 가능하게)

### 데이터 단위 — 2단계 설계

```
[1단계 — 현재]
센터/가정 + 세션 + 아이 이름(입력)
→ 당일 기록 조회. 누적은 아직 안 됨.

[2단계 — 확장]
아이를 사전 등록(children 테이블)
→ 플레이 시 아이 선택 → child_id 로 데이터 누적
→ 개인별 성장 그래프 / 학부모 리포트 개방
```

핵심은 **1단계 데이터가 2단계에서 버려지지 않는 것**. `child_id`를 처음부터 nullable로 넣어두고, 아이 등록 후 이름 매칭으로 소급 연결한다.

### 확장 로드맵

```
1단계 (현재)   세션 + 이름 입력, 당일 기록
2단계          아이 등록 → child_id 누적, 개인 성장 그래프
3단계          학부모 계정 + 성장 리포트
4단계          역량 기반 게임 추천 / 리그 / 캐릭터 성장
```

## 9. 열린 질문

1. **다인 플레이(2~4명) 인식** — MediaPipe Pose는 기본 1인 추적. 카드의 인원 배지가 "동시 인식"인지 "번갈아 플레이"인지 정의 필요. 작업량이 완전히 달라진다.
2. **폰 성능 하한선** — 어느 사양까지 지원할지. 구형 폰에서 프레임이 떨어지면 반응속도 측정이 부정확해진다.
3. **게임 50개 이후의 홈 화면** — 지금 구조는 40~50개까지 유효. 그 이후엔 "전체"가 기본값이면 안 되고 필터가 걸린 상태가 기본이 되어야 한다.
4. **머무르기 시간 기본값** — 1.2초는 가설. 실제 아이들 반응으로 확정 필요.
5. **데이터 프라이버시** — 가정 사용이 늘면 아이 정보 저장에 대한 동의 절차가 센터보다 더 중요해진다.
