## 1. 무엇을 만드는가

AI 모션인식 기반 유아체육 게임 **허브 플랫폼**.
아이가 몸을 움직여 게임을 즐기고, 그 움직임이 곧 조작이 되며, 결과가 **운동 데이터로 누적되어 성장 리포트로 연결**된다.

### 세 개의 축

```
① 게임 허브        플레이 제라 = 게임팩이 꽂히는 플랫폼
② 몸으로 하는 조작  손 포인터 + O/X — 손에 아무것도 안 듦
③ 운동 데이터      플레이할수록 아이의 운동 기록이 쌓임
```

**③이 존재 이유다.** 게임은 데이터를 모으는 즐거운 수단이고, 허브는 그 게임들을 담는 그릇이며, 조작 체계는 아이가 도구 없이 참여하게 만드는 인터페이스다.

> 이 순서를 뒤집으면 "모션 게임 모음"이 된다. 게임은 유행이 지나지만 아이의 운동 데이터는 사라지지 않는다.

### 핵심 가치

- 아이들이 화면을 보고 **실제로 몸을 움직이게** 만드는 콘텐츠
- **손에 아무것도 들지 않고** 몸만으로 게임 전체를 조작
- **폰 하나만 있으면** 어디서든 시작 — 설치도, 기기 연결도, 계정도 없이
- 센터 수업 → 운동 데이터 누적 → 학부모 리포트 → 콘텐츠 사업

### 파트너십

- **자파리센터** — 테스트베드, 유아 스포츠 교육 전문
- 1차 테스트 2026-07-08 완료 · 센터 코드 `ZAFARI2026`

## 2. 실행 환경 — 폰이 본체, TV는 모니터

v1의 문제는 멀티디바이스라서가 아니라 **폰을 센서로만 쓰고 두뇌를 다른 기기에 뒀기 때문**이다. 매 프레임 포즈 데이터를 네트워크로 흘려야 했고, 세션 코드로 페어링해야 했고, 끊기면 게임이 죽었다.

폰이 전부 하면 이것이 통째로 사라진다.

```
[폰 하나가]  카메라 + MediaPipe + 게임로직 + 렌더링 + 조작
     ↓  미러링 / HDMI
[TV는]  화면만 띄움 — 스마트 TV든 구형이든 무관
```

### 세팅 티어

| | 구성 | 페어링 | 지연 | 주 사용처 |
|---|---|---|---|---|
| **A** | 폰 + HDMI → TV | ❌ | 없음 | 가정 (최적) |
| **B** | 폰 + 미러링 → TV | ❌ | 100~200ms | 가정 (최다) |
| **C** | 폰·태블릿 단독 | ❌ | 없음 | TV 없는 집, 여행 |
| **D** | 노트북 + USB 웹캠 | ❌ | 없음 | 자파리센터 |

**네 가지 모두 페어링이 없다.** 웹앱 하나가 그대로 돌아간다.

### TV 브라우저를 쓰지 않는 이유

TV엔 카메라가 없고, 삼성 Tizen은 외장 웹캠 연동이 안 되며, LG webOS는 같은 TV에서도 앱마다 갈린다. **웹 되는 TV든 아니든 폰이 필요하다는 결론이 같다.**

### 세팅 안내에 반드시 들어갈 것

- **충전 연결** — 카메라 + AI + 미러링 동시 구동은 20분이면 스로틀링이 온다
- **가로 거치** · **거리 1.5~2m** (앱이 자동 판정해 안내)

### ⚠️ 아직 검증되지 않은 전제

**미러링(AirPlay) 중에도 카메라가 유지되는가** — 티어 B의 전제인데 확인된 적이 없다. 티어 B가 "가정 최다"로 상정돼 있으므로, 여기가 막히면 실행 환경 전략을 다시 짜야 한다.

## 3. 조작 체계 — 세 층 ✅ 전부 구현

| 층 | 수단 | 쓰는 곳 | 상태 |
|---|---|---|---|
| **목록 선택** | 손 포인터 + 머무르기 | 허브, 인트로 | ✅ `core/pointer.js` |
| **확인 · 전환** | O / X | 스타트, 준비, 종료 확인, 게임오버 | ✅ `core/pose/gesture.js` |
| **게임플레이** | 게임별 모션 | 플레이 중 | ✅ 게임팩마다 |

> v3 초판은 "메뉴=포인터 / 게임 중=O/X"로 적었다가 정정됐다. **O/X는 메뉴·화면 전환용**이고 게임플레이는 레인·점프·숙이기·포즈매칭이다.

### 손 포인터 (STEP 6 완료)

- 손목(15/16)만 사용 — Hands 모델을 얹으면 프레임이 절반이 된다
- 활성 박스는 **어깨 너비 기준** 자동 스케일 → 아이/어른·거리 무관
- One Euro Filter 필수 — 없으면 조준이 안 된다
- 손을 어깨 위로 들면 활성, 내리면 비활성
- 경계 히스테리시스 12px

**머무르기 시간** (03 화면설계 기준)

| 대상 | 시간 | 근거 |
|---|---|---|
| 게임 카드 · 시작하기 | 1.2초 | 잘못 누르면 게임이 바뀐다 |
| 카테고리 · 필터 | 0.6초 | 목록이 바뀌어 놀랄 수 있다 |
| 페이지 이동 | 0.5초 | 되돌리기 쉽다 |

**머무르기 감소는 두 갈래다.** 버튼 사이로 미끄러지면 `dt × 0.6`으로 천천히 줄지만, 다른 버튼으로 옮기면 즉시 0이다. 진행도를 물려주면 엉뚱한 버튼이 눌린다. 손 떨림에는 관대하고 의도적 이동에는 단호해야 한다.

### 카메라를 언제 켜는가

손을 보려면 카메라가 먼저 켜져 있어야 해서 **"손 들면 켜기"는 불가능하다.**
→ 첫 번은 버튼, 이후 기억.

> **iOS는 `getUserMedia`를 사용자 제스처 안에서만 허용한다.** 자동 시작을 "첫 탭 한 번"으로 미뤘다. 데스크톱에선 차이가 없고 아이폰에선 이게 유일한 방법이다.

**v3 대비** — `hero`(히어로 배너용 와이드 이미지) 추가, `skills` 제거(`tags`와 중복), `rounds`는 게임별 확장 필드로 유지.

> `hero`가 없으면 썸네일을 블러 처리해 배경으로 쓴다. 새 게임에는 **1920×1080급 와이드 이미지**를 같이 넣는 게 좋다.

### 왜 카테고리가 아니라 태그인가

카테고리를 **구조**로 쓰면 게임마다 "어느 칸에 넣지?"를 정해야 하고, 그 순간 분류가 기획을 제약한다. 점프도 협동도 하는 게임은 어디에 두는가?

| | 카테고리 = 구조 | 태그 = 필터 |
|---|---|---|
| 게임의 위치 | 한 칸에만 존재 | 목록에 항상 있음 |
| 다중 분류 | 중복 노출 문제 | 자연스럽게 모두 걸림 |
| 개발할 때 | 칸에 맞춰 기획 | **만들고 나서 태그만 붙임** |

홈의 기본 상태는 "전체"이고, 필터는 선생님이 "오늘은 하체 위주로" 할 때 쓰는 도구다.

## 5. 홈 화면 — 고정 히어로 + 한 줄 페이징

```
┌──────────────────────────────────────────────────┐
│  PLAY ZERA              [✋ 손][👤 제라][☰]      │
│                                                  │
│   4-8세 · 순발력 · 피하기    [ 선택된 게임 비주얼 ]│  ← 고정
│   똥 피하기                                       │
│   [▶ 시작하기]                                    │
├──────────────────────────────────────────────────┤
│  전체 게임 20 · 2/5              [⚙ 전체 ▾]      │
│  ┌────┐┌────┐┌────┐┌────┐                       │  ← 한 줄만
├──────────────────────────────────────────────────┤
│  ⤒ 맨 위로 │ ▲ 위로 │ ▼ 아래로 │ ⤓ 맨 아래로   │
└──────────────────────────────────────────────────┘
```

### 자유 스크롤을 버린 이유

카드 클릭이 "선택"이고 실행은 히어로에서 하는데, **스크롤로 히어로가 사라지면 선택의 결과가 안 보인다.** 클릭만 두 번 하고 아무 일도 안 일어난 것처럼 느껴진다.

그리고 **손 포인터 머무르기가 1.2초인데 조준하는 동안 카드가 움직이면 못 맞춘다.** 위치 고정이 사실상 전제 조건이다.

03 설계의 하단 4칸 바도 원래 "한 줄씩" 이동이다. 자유 스크롤 쪽이 예외였다.

### 실행 지점을 하나로 몬 이유

카드 클릭 = **선택**, 실행 = 히어로의 `▶ 시작하기` 하나뿐.
아이가 목록을 훑다가 잘못 눌러 게임이 켜지는 사고가 없다.

### 페이지 구성

```
0페이지   이어서 하기 (기록 있을 때만 · 좌우로 넘김 · 최대 8개)
1~n페이지 전체 게임 4개씩
```

이어서 하기를 세로로 나누지 않는 이유 — 전체 게임은 훑는 목록이고, 이어서 하기는 "어제 하던 거"를 집는 자리다. 세로 페이지를 잡아먹으면 전체 게임까지 가는 길이 길어진다.

### ⚠️ 카테고리 필터가 필수가 됐다

20개면 5페이지, 50개면 13페이지다. 03 설계는 "50개 이후엔 전체가 기본값이면 안 된다"고 썼는데, 이 구조에서는 그 시점이 앞당겨진다. **실제 게임이 20개를 넘으면 첫 화면 기본 필터를 정해야 한다.**

## 6. 운동 데이터 ★ 플랫폼 핵심

```
아이가 논다 → 움직임이 측정된다 → 데이터가 쌓인다
                                      ↓
                          가정: 우리 아이 성장 기록
                          센터: 수업 효과 근거
                          사업: 축적된 유아 운동 데이터셋
```

### 첫 기록 (2026-08-02 21:01 KST)

```
warmup-obstacle · 1세션 · 활동 36초 · 점프 2 · 앉기 3 · 피하기 6
```

파일 저장 방식이던 시절엔 재배포마다 사라졌다(Render 배포본 기록 0건). Supabase로 옮기고 나서야 남기 시작했다.

### 신뢰할 수 있는 데이터만 센다

| `input_mode` | 의미 | 운동 통계 |
|---|---|---|
| `motion` | 카메라로 몸 인식 | ✅ 집계 |
| `keyboard` | 키보드·터치 조작 | ❌ 제외 |
| `unknown` | 초기 임포트 33건 | ❌ 제외 |

점프·앉기 카운트는 **몸 동작 횟수**를 센다. 운동량 지표로는 올바른 설계지만, 키보드 모드에서는 방향키만 눌러도 올라간다. 손가락 운동이지 유아체육이 아니다. 개발·검증이 대부분 키보드로 이뤄지므로 구분하지 않으면 "이 아이 이번 달 점프 300회"에 테스트가 섞인다.

→ `exercise_summary` 뷰는 `motion`만 본다.

### `duration_sec`이 아니라 `active_sec`

타이틀·카메라 준비·튜토리얼에 머문 시간이 운동량으로 잡히던 버그가 있었다(실측: 58초 기록 중 실제 활동 6초). 기준점을 카운트다운 직후로 옮겼다.

> **임포트된 33건은 교정 전 값이다.** 리포트에서 `duration_sec`을 운동량으로 쓰면 안 된다.

### 저장 경로가 다섯이다

미션 완료 · 게임오버 · 종료 · 탭 닫기 · 라우팅 이탈.
경로가 하나면 되거나 안 되거나지만, **다섯이면 "두 번 저장"과 "아무도 저장 안 함"이 둘 다 생긴다.**

`runId`(판 식별자) + `_saved`(멱등 플래그) 두 장치가 그 경계를 지킨다. 백그라운드 전환이 몇 번 일어나도 큐는 1건이고, 나중에 완주하면 그 기록이 큐를 대체한다.

## 7. 기술 구조 — 값비싸게 배운 규칙 넷

### ① 카메라는 앱 전체에서 하나다

`poseEngineCore.acquire()` / `release()` 참조 카운팅.
화면마다 열고 닫으면 허브→인트로→게임 사이에 세 번 재시작하고, 그때마다 커서가 끊기며 방금 닫은 장치를 바로 여는 동안 `NotReadableError`가 난다.

추론은 화면에 붙지 않는 자체 video에서 돌리고, 표시용 `<video>`들은 같은 스트림을 나눠 쓴다.

> 추론용 video도 **DOM 안에 있어야 한다.** 붙이지 않으면 브라우저가 디코딩을 건너뛰어 `currentTime`이 멈추고, 랜드마크가 한 번도 안 나온다. PIP는 다른 video라 영상이 잘 나오므로 "화면은 보이는데 인식만 안 되는" 모양이 된다.

### ② 좌표는 거울 좌표 하나다

엔진이 `1 - x`를 **한 번만** 한다. 구독자는 뒤집지 않는다.
이전에는 게임마다 달라서(똥 피하기는 `selfieMode`, 웜업은 `motionDetector` 안에서) 합치는 순간 한쪽이 반드시 뒤집혔다.

반전을 스무딩보다 **먼저** 한다. 순서를 바꾸면 두 좌표계가 한 배열에 섞인다.

### ③ 정리는 라우터의 `onLeave`로 한다

페이지가 `hashchange`를 직접 들으면 라우터 리스너가 먼저 걸려 있어 **이미 `#app`이 비워진 뒤에** 정리가 돈다. 웹캠을 늦게 끊으면 다음 화면에 카메라 표시등이 남는다.

### ④ 전역 스위치를 공유 자원에 걸지 않는다

`setPaused()`가 공유 엔진을 통째로 멈춰서 한 화면이 나가며 pause를 걸자 **다른 화면의 손 포인터까지 굶었다.** 전역 스위치 대신 구독으로 판단한다 — 아무도 안 듣고 있으면 추론하지 않는다.

## 10. 열린 질문

1. **다인 플레이 인식** — MediaPipe Pose는 기본 1인 추적. 카드의 인원 배지가 "동시 인식"인지 "번갈아"인지 정의 필요. **작업량이 완전히 달라진다.**
2. **폰 성능 하한선** — 지금은 WASM SIMD(iOS 16.4+)로 자른다. 실기기에서 프레임이 안 나오면 더 올려야 한다.
3. **미러링 중 카메라 유지** — 티어 B의 전제. 미검증.
4. **머무르기 1.2초** — 어른 기준으로 맞춘 가설. 실제 아이 반응으로 확정 필요.
5. **게임 20개 이후 홈 기본 필터** — 5페이지를 넘어가면 "전체"가 기본이면 안 된다.
6. **데이터 프라이버시** — 가정 사용이 늘면 아이 정보 동의 절차가 센터보다 더 중요해진다.
7. **똥 피하기 난이도** — 조준 낙하로 실질 난이도가 올라갔다. 라운드 5(1.2초 간격)를 아이가 따라올 수 있는지 미확인.
