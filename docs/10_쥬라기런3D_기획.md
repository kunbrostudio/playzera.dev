# 쥬라기 Run 3D — 기획

> 새 게임이다. **기존 셋(우주·정글·쥬라기)은 건드리지 않는다.**
> 원본 지시서: `STEP_쥬라기런_3D배경_작업지시서.md` (ken, 8/18)

---

## 1. 무엇을 만드나

컨셉아트에 가까운 **3D 러너**. 지금 러너가 2.5D(가짜 원근)로 내는 느낌을
진짜 원근으로 바꾸고, **바닥과 배경이 한 덩어리로** 흐르게 한다.

규칙은 새로 만들지 않는다. 레인 판정 · 코스 타이밍 · 포즈 감지 · 기록 저장은
지금 것을 그대로 쓴다. **3D는 보이는 것만 바꾼다.**

---

## 2. 왜 "배경만 3D"가 아닌가 ★

지시서는 좌우 배경만 3D로 올리고 트랙은 2D로 두자고 한다. 속도를 공유해도
이건 **어긋난다** — 두 원근이 다른 곡선이기 때문이다.

| | 깊이 → 화면 y |
|---|---|
| 지금 트랙 (`world.js`) | `y = HORIZON + (H-HORIZON)·p` — **깊이에 선형** |
| 3D 카메라 | `y ∝ 1/z` — **반비례** |

같은 속도로 밀어도 야자수는 처음에 천천히 오다 급격히 커지고, 트랙 무늬는
일정하게 온다. 붙여 놓으면 **배경이 트랙 위를 미끄러진다.**

지금 트랙이 선형인 건 실수가 아니다. 셰브론·연석·바닥 광택이 전부 같은 `p`를
공유해야 손으로 맞출 수 있어서 그렇게 정했다(STEP 12). 그 선택이 3D와 안 맞는 것뿐이다.

**그래서 바닥까지 3D로 간다.** 바닥이 3D면 그 위에 서는 장애물과 캐릭터도 같은
좌표계여야 한다. 결국 세계 전체가 3D다.

---

## 3. 무엇이 3D이고 무엇이 아닌가

| 층 | 무엇 | 어떻게 |
|---|---|---|
| 원경 | 하늘 · 능선 · 화산 | **2D 판 한 장.** 멀어서 시차가 없다 — 3D로 만들 이유가 없다 |
| 중·근경 | 야자수 · 바위 · 알 · 공룡 | 3D 저폴리 (`InstancedMesh`) |
| 바닥 | 흙길 · 잔디 · 연석 | **긴 판 하나 + UV 스크롤** |
| 그 위 | 장애물 · 관문 · 출발선 | 3D. 코스 타이밍은 지금 것 그대로 |
| 주인공 | 아이 | **빌보드 스프라이트.** 지금 그림 13장을 그대로 세운다 |
| UI | HUD · 힌트 · 화살표 | 지금처럼 DOM/2D. 3D 위에 얹는다 |

**바닥을 UV 스크롤로 하는 게 "하나처럼"의 핵심이다.** 지오메트리를 움직이지
않으니 이음매가 원천적으로 없다. 프롭은 그 위를 z로 흐르고, 둘이 같은 카메라를
보므로 속도가 저절로 맞는다 — 맞추는 코드가 필요 없다.

> **캐릭터를 빌보드로 두는 이유.** 3D 모델로 가면 리깅·달리기 애니메이션이 새
> 작업이고 남·여 두 벌이 필요하다. 빌보드는 만들어 둔 그림을 그대로 쓴다.
> 카메라가 뒤에서 따라가는 러너라 각도가 거의 안 변해서 티가 잘 안 난다.

## 4. 성능 — 가장 큰 위험은 MediaPipe와의 GPU 경합

포즈 인식과 3D 렌더가 **같은 GPU를 나눠 쓴다.** 이건 설계로 장담할 수 없고
**측정으로만** 답할 수 있다. 그래서 에셋을 발주하기 전에 게이트를 둔다(§5의 0단계).

### 예산

| 것 | 상한 | 왜 |
|---|---|---|
| draw call | 20 이하 | 프롭 종류당 1(인스턴싱) + 바닥 + 하늘 + 장애물 |
| 재질 | **1개** | 512² 아틀라스 하나에 모든 프롭 |
| 실시간 조명 | **0개** | 라이팅은 버텍스 컬러에 굽는다. `MeshBasicMaterial` |
| 그림자 맵 | **0개** | 발밑 그림자는 바닥 텍스처에 그린 원 |
| 프롭 폴리 | 500~1500 tri | 저폴리. 실루엣만 살린다 |
| GLB 전체 | 2MB 이하 | Draco 또는 meshopt |
| 카메라 far | ~120 유닛 | 안개로 스폰 거리를 감춘다 |
| DPR | 1.5 상한 | 레티나에서 픽셀 수가 4배가 된다 |
| 포즈 추론 | 20~24fps 캡 | 지금은 rAF마다 돈다. 사람 동작은 24fps면 충분하다 |

### 자동으로 낮추기

FPS를 재서 **50 아래로 3초 지속**되면 순서대로 낮춘다.

1. DPR 1.5 → 1.0
2. 프롭 밀도 −40%
3. 중경 프롭 끄기 (근경만 남긴다)

아이는 프롭이 줄어든 걸 모른다. **끊기는 건 안다.**

### 번들

`three`는 이 게임에서만 **동적 import**한다. 다른 게임과 허브 번들에 들어가면
안 된다 — 지금 전체가 350KB인데 three 코어만 그만큼 된다.

## 5. 단계 — 하나씩, 앞 단계가 통과해야 다음

### 0단계 — 성능 게이트 (에셋 없이) ★  — **뼈대 완료 8/18**

`#/lab3d`에서 잰다 (DEV 전용). `npm run dev` → `localhost:5173/#/lab3d`

만든 것

```
src/games/runner3d/
  curve.js   곡률 — 논리는 평면, 눈에만 휜다 (정본)
  props.js   InstancedMesh + 되돌리기
  scene.js   씬·바닥 UV 스크롤·재질 하나
src/pages/lab3d.js   FPS·draw call·곡률 슬라이더·포즈 동시 실행
```

**`three`는 `lab3d.js`에서 동적 import한다.** 프로덕션 번들(351KB)에 안 들어가는 것을
빌드 결과로 확인했다 — 라우트가 `import.meta.env.DEV`에서만 등록된다.

`#/lab3d`에서 볼 것

| 값 | 통과 |
|---|---|
| 렌더 FPS | 55 이상 |
| 포즈 FPS | 20 이상 (**포즈를 켠 채로** 재야 의미가 있다) |
| draw call | 20 이하 |

슬라이더로 휨을 돌리면 "이 휨을 **진짜 구로** 만들면 지평선이 몇 유닛에서 끊기는지"를
같이 보여준다. 왜 셰이더로 가는지가 화면에서 숫자로 보인다.

### 0단계에서 정해진 것 (8/19)

| | |
|---|---|
| **곡률** | **R = 600.** 60~900을 돌려 보고 눈으로 골랐다. 더 작게 하면 휨은 극적이지만 바닥 판 끝이 지평선 위로 들려 잘린 선이 보이고, 아이가 보기에 어지럽다 |
| **성능** | 데스크톱에서 렌더 120fps · 포즈 30fps · draw call 7 · 삼각형 4,304 — **통과** |

곡률을 화면에서 정한 게 맞았다. `R=110`은 숫자로는 극적인데(58유닛 앞이 15유닛 낙차)
실제로 보니 바닥 끝이 하늘에 잘린 선으로 남았다 — **숫자로는 안 보이는 것이었다.**

### 겪은 것 — 땅만 반대로 흘렀다 ★

좌우 나무는 다가오는데 **바닥만 앞으로 밀려갔다.** 한 화면에서 두 방향이 보이니
멀미가 났다. UV offset 부호 하나였다.

판을 눕히면 텍스처의 +v가 **먼 쪽**을 향한다. 샘플링이 `uv·repeat + offset`이므로
offset을 **키워야** 먼 쪽 무늬가 가까운 자리에 나타난다 = 카메라 쪽으로 온다.
`-=`로 뒀던 것을 `+=`로 바꿨다.

### 겪은 것 — 트랙이 네 줄로 늘어났다

잔디와 흙길을 한 텍스처에 그리고 가로로 4번 반복했더니 흙길이 네 줄이 됐다.
**잔디는 촘촘히 반복해야 결이 살고 트랙은 반복하면 안 된다** — 한 장에 두면
둘 중 하나를 포기해야 한다.

판을 둘로 나눴다(`ground.js`). draw call 하나가 늘 뿐이다.
트랙은 가로 반복 없이(`ClampToEdge`) 한 장이 폭을 그대로 덮고, 그 위에 차선 둘을
그려 **3등분**한다 — 2D 러너에서 배운 것 그대로다(STEP 15).

**여기서 답이 안 나오면 나머지는 의미가 없다.** 데스크톱 · 아이패드 · 안드로이드
보급형에서 각각 재고, 통과한 뒤에 에셋을 발주한다. 곡률도 여기서 눈으로 정한다 —
숫자로는 못 정하고, 정해 두면 에셋 발주 때 "이 각도에서 이렇게 보인다"가 기준이 된다.

### 1단계 — 세계의 뼈대  — **완료 8/19**

```
backdrop.js   원경 — 능선·화산을 **2D 판**으로. 지금 쥬라기 그림 그대로
character.js  주인공 — 빌보드 + 달리기 아틀라스 + 레인 보간
ground.js     잔디 판 + 트랙 판 (3등분 차선)
```

**원경도 곡률을 받는다.** 판이 하나의 z에 평평하게 서 있으므로 찌그러지지 않고
통째로 내려앉는다 — 그래야 휜 바닥의 지평선과 능선 밑동이 붙는다. 곡률을 안 주면
바닥은 내려가는데 능선만 제자리라 사이가 벌어진다.

안개는 안 받는다. 안개는 스폰 거리를 감추려고 있는 것이고, 원경은 감출 게 없다.

**캐릭터는 달리기 5컷을 한 장 아틀라스로 묶고 UV만 옮긴다.** 프레임마다
`material.map`을 갈아 끼우면 텍스처 바인딩이 초당 12번 바뀐다. 한 장이면 한 번이다.

> 컷마다 가로세로가 달라(435×900 ~ 476×900) 칸 폭을 가장 넓은 것에 맞추고
> **발밑을 기준으로** 정렬했다. 위로 맞추면 키 작은 컷이 공중에 뜬다.

레인은 **논리(정수)와 화면(보간된 x)을 따로 둔다.** 정수만 쓰면 순간이동하고,
실수만 쓰면 "지금 몇 번 칸인가"를 판정이 알 수 없다. 레인 간격이 트랙 폭의 1/3과
같은지는 테스트가 본다 — 어긋나면 **아이가 선 자리와 그려진 차선이 다르다.**

### 2단계 — 게임을 붙인다  — **코스·자세 완료 8/19**

```
character.js   자세 11컷 아틀라스 + 상태(달리기·점프·숙이기·자세)
course3d.js    기존 course.js를 **import**해 쓴다. 시간 → 거리 환산만 새로
obstacles3d.js 종류별 InstancedMesh. 도형은 0단계 것
```

**코스를 복사하지 않았다.** `runner/game/course.js`가 만드는 타임라인을 그대로
`import`한다. 레벨별 사이클, 큐브 6 → 허들 6 → 자세 3, 간격을 speed로 나누는 것까지
전부 거기 있다.

복사했다면 오늘 고친 밸런스를 다음에 두 번 고쳐야 하고, 더 나쁜 건 **두 게임의
운동량이 다른 뜻**을 갖게 되는 것이다 — 같은 레벨 5인데 판이 다르면 기록을 못 견준다.
두 코스가 같은 이벤트·같은 `hitTime`을 내는지 테스트가 본다.

여기서 새로 하는 일은 하나다.

```
z = -(hitTime - now) × speed × UNITS_PER_SPEED
```

2D 러너는 `approachSec` 전에 화면 위에 띄우고 `p`를 0→1로 밀었다. 3D는 제자리에
두면 된다 — **세계가 흐르니까 거리가 곧 남은 시간이다.**

> z를 저장해 두고 빼 나가지 않는다. **판정의 정본은 시간**이고 z는 그려 보이는 값이라
> 매 프레임 다시 계산한다. 빼 나가면 부동소수 오차가 쌓여 레벨 끝에서 어긋난다.

### 자세 — 점프는 두 컷이다

| 상태 | 컷 | 왜 |
|---|---|---|
| 달리기 | `run01~05` | 12fps |
| 점프 | `jump_prep` → `jump_air` | 한 컷으로 때우면 **발을 굴렀는지 그냥 떠올랐는지** 못 읽는다. 앞 0.14초가 구르는 순간이다 |
| 숙이기 | `slide` | **누르고 있는 동안 유지.** 떼도 0.55초는 남는다 — 떼자마자 일어나면 허들 아래에서 머리가 튀어나온다 |
| 자세 | `stretch_*` | 요가 구간 |

숙일 때 스프라이트를 **눌러 그리지 않고 아래로 내린다.** 눌러 그리면 아이가
납작해져서 다른 캐릭터로 보인다.

컷마다 가로가 달라(435×900 ~ 886×900) 칸 폭을 가장 넓은 것에 맞추고 가운데 정렬,
세로는 **발밑 기준**으로 정렬했다. 안 맞추면 자세가 바뀔 때 아이가 좌우로 튄다.

### 겪은 것 — 웅크린 아이가 거인이 됐다 ★

숙이기와 런지가 달리기보다 훨씬 커 보였다.

원인은 그림이다. **12장이 전부 900px 높이인데 저마다 꽉 차게 잘려 있다.**
웅크린 슬라이드도 900, 서서 달리는 컷도 900이다. 그대로 그리면 웅크린 아이가
선 아이와 **같은 키**가 된다.

그림 파일은 "이 자세의 실제 키"를 모른다. **코드가 알아야 한다.**
서 있는 달리기를 1.0으로 두고 컷마다 배율을 적었다 — 슬라이드 0.52, 런지 0.72,
점프 준비 0.86. 가로세로를 같이 줄인다(세로만 줄이면 납작해져 다른 캐릭터가 된다).

> 앞서 넣었던 `duckDrop` 눌러 그리기는 걷어냈다. 컷마다 배율이 생겼으니
> 두 곳이 같은 일을 하게 된다 — 그러면 반드시 어긋난다.

### 겪은 것 — 큐브 셋이 같은 칸을 막았다 ★★

좌우 피하기에서 **세 개가 연달아 같은 칸**에 나왔다. 아이는 한 번 비키면
나머지 둘은 그냥 지나갔다 — 세 번 중 한 번만 운동이 된 것이다.

원인: `far` 안이면 다 그렸다. 큐브가 여럿 **같은 순간에** 시야에 들어왔고,
레인을 그때 정하니 전부 그 순간의 아이 자리를 막았다.

2D 러너는 `approachSec` 전에 하나씩 띄운다. 같은 규칙으로 바꿨다.
큐브 간격 3.0초 · 예고 3.2초라 **하나씩 차례로** 나타나고, 그 사이 아이는 이미
옆 칸으로 옮겨 가 있다. 그래서 방향이 저절로 번갈아 바뀐다.

> 거리로 자르면 안 되는 이유가 이것이다. 레벨이 오르면 같은 `far` 안에 더 많이
> 들어와서 증상이 더 심해진다. **시간이 기준이다.**

### 자세 키는 A·S·D

기존 러너의 키보드 모드와 같다(`screens.js`의 안내). 게임마다 키가 다르면
아이가 매번 다시 배운다. 숙이기처럼 **누르고 있는 동안** 유지된다.

### 반응형 — 지금 잡았다 ★

**세로 화각(`fov`)을 고정하면 안 된다.** 화면이 좁아질수록 가로로 보이는 폭이 준다.
데스크톱 16:9에 딱 맞게 잡아 두면 태블릿 4:3에서 **트랙 좌우가 잘린다** —
바깥 레인의 장애물이 화면 밖에서 나타난다. 그건 반응이 아니라 운이다.

계산해 보면 fov 55 고정 시 4:3에서 보이는 가로 폭이 **14.3유닛**으로,
트랙 15유닛이 안 들어간다.

그래서 반대로 간다. **"캐릭터 자리에서 가로 19유닛이 보인다"를 못 박고** 세로 화각을
비율에서 계산한다(`fovFor`). 화각은 50~70도로 묶는다 — 넓히면 어지럽다.

| | 세로 화각 | 보이는 가로 폭 |
|---|---|---|

| 폰 가로 19.5:9 | 50° | 20.2 |

**왜 지금인가.** 이 값이 트랙 폭과 프롭 크기를 정하고, **에셋 발주 규격이 거기 매여

지금은 한 줄이고 나중은 그림 전부다.

> 세로로 든 폰은 이 방법으로도 안 된다 — 가로 6유닛밖에 안 보인다.

### 원경 — 판을 걷어내고 띠로 (8/20) ★★

화면에 **화산만** 떠 있었다. 능선은 어디에도 없었다. 원인은 그림이 아니라 **곡률**이다.

원경을 평면으로 세우고 곡률 셰이더를 같이 먹였는데, 셰이더는 `y -= k·z²`를 한다.
118유닛 앞의 판은 통째로 **11.4유닛 내려앉는다.** 능선(밑동 y=−2)은 지평선 밑으로
파묻혔고, 더 높이 띄워 뒀던 화산(밑동 y=4, 높이 34)만 남아 하늘의 스티커가 되었다.

> **원경에 곡률을 주지 않는다.** 멀리 있는 것은 지평선에 붙어 있는 것이고,
> 지평선은 세계가 휘어도 그 자리다. 곡률을 받아야 밑동이 붙는다고 생각했던 게 틀렸다.

#### 그럼 어디에 붙이나 — 세계가 접히는 선

휜 바닥에는 **끝나는 선**이 있다. 거리 `d`의 지면이 눈 아래로 보이는 각은

```
tan θ(d) = (h + k·d²) / d        (h = 카메라 높이)
```

이고, 이 값은 `d = √(h/k)`에서 **가장 작아진다** — 더 멀어지면 다시 내려간다.
즉 바닥은 지평선까지 가지 않고 그 각도에서 접힌다.

```
tan(접힘각) = 2·√(k·h)
```

지금 값(k = 1/1200, h = 6)으로 **8.05°, 85유닛 앞.** 원경 띠의 지면선을 정확히
이 각도에 두면 바닥이 끝나는 자리에서 그림이 이어 받는다. 곡률 슬라이더를 돌리면
띠도 같이 오르내린다(`backdrop.setCurve`).

식과 "판이 왜 안 됐나"는 둘 다 테스트로 박아 뒀다 — 눈으로만 고치면 다음에 또 판을 세운다.

#### 왜 원통인가

평면 한 장은 좌우 끝이 가운데보다 멀어 원근이 어긋난다. 원통은 모든 방향이 같은 거리다.
카메라가 안 도니 **150°만** 두른다 — 360°는 절반 이상을 못 보고 버린다.
텍스처 2560px가 보이는 87°에 거의 1:1로 얹힌다.

| | 값 | 왜 |
|---|---|---|
| 반지름 | 116 | `far`(130) 안쪽 — 넘으면 하늘에 구멍이 뚫린다 |
| 두르는 각 | 150° | 최대 화각 87° + 여유 |
| 지면선 위 | 44° | 세로 화면(fov 상한 70°)에서도 하늘이 안 빈다 |
| 능선 장수 | **7 (홀수)** | 짝수면 이음매가 한가운데 와서 트랙이 벽으로 들어간다 |
| 화산 폭 | 12° | 줄이면 더 멀어 보인다 |

#### 그림은 발주하지 않고 합친다

능선·화산·구름은 이미 쥬라기 테마에 있다. 새로 그리면 같은 세계가 두 벌이 되고
한쪽만 고쳐지는 날이 온다. 시작할 때 캔버스에서 한 장으로 합쳐 감는다 —
**테마 그림을 바꾸면 원경이 따라 바뀐다.** 새 파일 0개, draw call 1개.

그리는 차례가 곧 앞뒤다: 하늘 → 구름 → **화산** → 능선. 2D에서 순서를 뒤집어
화산이 능선 앞으로 나온 적이 있다(STEP 16).

#### 안개를 뒤로 물렸다

55~120 → **88~142**, 색도 하늘색이 아니라 연한 풀빛으로 바꿨다.
안개가 지평선을 감추는 역할을 하고 있었는데 이제 **띠가 지평선을 닫는다.**
가까이 두면 접힘선 근처 잔디가 하늘색으로 바래고, 그건 원경이 아니라 **바랜 자국**으로
보인다 — 2D에서 이미 겪은 것이다(`CLAUDE.md`: 하늘색을 바닥에 얹지 않는다).
지금 안개가 하는 일은 프롭이 되돌아오는 자리(≈126유닛)를 무르게 하는 것뿐이다.

#### 겪은 것 — 연석을 `BoxGeometry`로 만들면 안 된다 ★

three의 상자는 **면마다 uv 축이 다르다.** 옆면은 `v = 높이`이고 윗면은 `v = 길이`다.
그래서 `offset.y`를 흘리면 윗면만 앞으로 오고 옆면은 위아래로 미끄러진다 —
바닥에서 부호 하나로 겪었던 "한 화면에 두 방향" 문제가 그대로 돌아온다.

단면을 길이 방향으로 미는 함수(`extrudeStrips`)를 직접 만들어 네 면 전부
`v = 길이`로 맞췄다. 덤으로 좌우 두 줄이 **한 지오메트리**라 draw call 하나다.
테스트가 "같은 단면 위의 두 점은 v가 같고 u는 다르다"를 본다.

### 구름이 흐른다 (8/20)

두 번 고쳤다. 첫 판은 원통에 감아 `u`를 돌렸는데, 구름이 **옆으로 미끄러졌다** —
달리는 게 아니라 제자리에서 도는 것처럼 보였다. 아래의 나무·돌은 다가와서
지나가는데 하늘만 옆으로 흐르니 **한 화면에 두 방향**이 보인 것이다.
바닥 UV 부호를 뒤집었을 때와 같은 종류의 문제다.

그래서 프롭과 같은 방식으로 바꿨다.

- `z`를 흘리고 `span`(150)마다 되돌린다. **span을 뺄 뿐 자리를 다시 뽑지 않는다** — 새로 뽑으면 간격이 무너진다
- **곡률을 같이 받는다.** 그래야 멀리서 산 너머로 떠오르듯 들어온다. 원경 띠에 안 넣은 이유가 이것이다 — 띠는 지평선에 붙어 안 움직이는 것들의 자리다
- 모양은 화산 연기와 같은 **퍼프**다. 뭉치 하나가 조각 다섯이라 뭉게구름처럼 보이고, 그림 파일이 없다
- 되돌아온 직후 `fadeIn` 구간에서 서서히 나타난다. 안 그러면 먼 하늘에 툭 뜬다
- 달린 거리의 **절반만**(`drag` 0.5) 보탠다. 전부 보태면 나무처럼 스쳐 지나가 구름이 코앞에 있는 게 된다

자리와 흐름은 `makeCloudField()`로 떼어 뒀다 — 캔버스를 만드는 순간 브라우저 없이
확인할 수 없고, 그러면 "옆으로 미끄러지는가 다가오는가"를 눈으로만 보게 된다.
테스트가 z가 커지는 것과 간격이 안 무너지는 것을 본다.

능선은 여전히 안 움직인다. **달려도 그대로 있는 것이 멀다는 뜻**이다.

### 겪은 것 — 연석만 앞으로 갔다 ★

턱을 넣고 보니 **연석만 반대 방향**으로 흘렀다. 부호 하나였는데, 원인은 축이다.

눕힌 판(`rotation.x = -π/2`)은 `+v`가 **먼 쪽**을 향한다. 그런데 `extrudeStrips`는
`z = -length/2`(먼 쪽)에서 `v = 0`으로 시작해 가까워질수록 v를 키운다 —
**v의 방향이 반대**다. 그래서 트랙과 같은 부호로 흘리면 턱만 앞으로 간다.
`offset.y`를 빼는 것으로 고쳤고, 테스트가 "v는 가까운 쪽으로 자란다"를 못 박아 둔다.

|---|---|---|
| 예산(500~1500 tri) | 처음부터 맞는다 | 감량해야 맞는다 |
| "조금 더 어둡게" | 한 줄 | 처음부터 다시 |
| 저장소에 남는 것 | **만드는 방법** | 결과 파일 |
| 디테일 | 톤 저폴리 | 컨셉아트에 가깝다 |

25~90유닛 뒤에 있는 물건이라 디테일은 어차피 안 보인다. **실루엣에 예산을 쓴다.**

```
tools/blender/
  pzblender.py     공용 — 밝기 굽기 · 관 · 덩어리 · 잎 · 띠 · 내보내기 · 미리보기
  make_palm.py     야자수
  make_props.py    화석 바위 · 알 둥지 · 아기 공룡 둘
  make_obstacles.py 알 받침대 · 허들 · 관문 둘 · 자세 팻말 셋
  preview/         블렌더가 찍은 미리보기 (게임과 같은 조건으로 렌더한다)
public/assets/runner3d/{props,obstacles}/*.glb   합쳐 600KB
```

#### 규격 — 야자수에서 정하고 나머지가 따랐다

- 원점은 **발밑(z = 0)**. 안 그러면 프롭이 땅에 박히거나 뜬다
- 밝기는 **정점 색에 굽는다.** 게임에 실시간 조명이 0개다
- 바닥에 가까울수록 어둡게. 그림자가 없으니 이게 유일한 접지 신호다
- 부품은 **하나로 합친다.** 나뉘어 있으면 인스턴싱해도 부품 수만큼 그린다
- 블렌더는 Z-up, three는 Y-up. 내보내기가 바꿔 주므로 **블렌더에서 −Y를 보게** 만든다

#### 크기는 코드가 정한다 ★

장애물 치수는 `obstacles3d.js`의 `KINDS`에서 스크립트로 **간다.** 반대가 아니다 —
뛰어넘을 높이, 숙일 틈, 한 레인을 막는 폭은 **판정의 일부**다. 그림이 규칙을 바꾸면
아이가 화면을 보고 판단한 것과 판정이 어긋난다.

#### 겪은 것 — 세 번 다시 만들었다

| 무엇 | 왜 틀렸나 |
|---|---|
| 야자수 잎이 **글라이더 날개** | 곧게 뻗은 판이었다. 야자수를 야자수로 읽게 하는 건 **솟았다가 처지는 곡선**이다. 높이를 `rise·sin − droop·t²`로 주고 잎을 두 층으로 나눴다 |
| 화석 뼈가 **안 보임** | 바위가 공처럼 둥글어 앞면이 없었고, 뼈를 반지름 안쪽에 뒀다. 바위를 넓고 낮게 눌러 앞면을 만들고 뼈를 표면 밖으로 뺐다 |
| 알이 **하얗기만** | 점무늬를 구의 반지름으로 배치했는데 알은 눌린 타원이라 무늬가 **속에 파묻혔다.** 실제 반지름(rx·ry)을 써야 표면에 붙는다 |

셋 다 **렌더를 보고** 알았다. 숫자로는 안 보이는 것들이라 `pzblender.preview()`가
게임과 같은 조건(정점 색 발광, 조명 0개)으로 찍는다 — 블렌더 조명으로 예쁘게 찍으면
게임 화면과 다른 것을 보게 된다.

### 공룡 모션 — 뼈대를 안 쓴다 ★

GLB에 애니메이션을 담으면 스키닝 계산이 붙고, 무엇보다 **`InstancedMesh`가 스킨드
메시를 못 쓴다** — 공룡 열 마리면 열 번 그려야 한다.

몸통·머리·꼬리를 **따로 내보내 각각 인스턴싱**한다(`DinoRow`). draw call 셋이면
몇 마리든 그린다.

```
머리 행렬 = 몸통 행렬 × 붙는자리로 이동 × 흔들기
```

블렌더가 부위의 원점을 **붙는 자리**에 맞춰 두었기에(`export_parts`) 이렇게 곱하면
목이 몸에 붙은 지점을 축으로 돈다. 원점이 딴 데면 머리가 궤도를 돈다.

- 마리마다 **위상과 박자**가 다르다. 같으면 열 마리가 한 몸처럼 고개를 젓는다
- 꼬리는 머리와 **반대로** 흔든다. 같은 방향이면 몸이 통째로 도는 것처럼 보인다
- 공룡은 트랙을 **바라보게** 세운다. 아무 데나 보면 배경이 아니라 방목장이다
- **살아 있는 건 공룡뿐이다.** 다 움직이면 아이가 봐야 할 트랙에서 눈이 떠난다

### 남은 것 (3·4단계)

- 실기기에서 draw call·FPS 재확인 (프롭 종류가 늘었다)
- 자동 품질 낮추기 (FPS 감시)
- 실기기 검증 — 아이패드 · 안드로이드 보급형

### 3단계 — 진짜 에셋

- GLB 교체. 좌우 배치 흩뜨리기는 지금 규칙(`jOff`·`jSpread`·`jDepth`)을 그대로 옮긴다
- 원경 그림은 지금 쥬라기 것을 재사용

### 4단계 — 마감

- 자동 품질 낮추기
- 실기기 재확인
- `docs/04`에 STEP 기록

공통 규칙

- 이름은 디자인 쪽에서 온다 — registry가 파일명을 데이터로 든다(`CLAUDE.md` 규칙)
